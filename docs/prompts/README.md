# 分阶段提示词的用法

这个目录里是给 AI 编程助手的分阶段任务说明。一个会话只做一个阶段，做完就结束，下一个阶段开新会话。

## 为什么这样拆

长会话的上下文被压缩之后，模型容易忘记最初的目标和约束。这里用四样东西对付这个问题：

- **`CLAUDE.md`** 放所有阶段共用的规则：项目目标、架构不变量、代码规范。它每次会话都会被读到。
- **`docs/progress.md`** 是跨会话的记忆。每完成一个任务就更新，新会话靠它知道做到了哪里。
- **每个阶段的提示词** 写明这个阶段的目标、任务、不做什么、完成标准。它放在仓库里，模型在对话被压缩后可以重新读它。
- **质量闸门** 把代码规范变成机器检查：`ruff`、`mypy`、`pytest`。其中 `tests/test_code_health.py` 检查模块之间的依赖方向、文件和函数的行数、嵌套层数、文件编码、忽略检查的注释有没有写原因。它从第一天起就在仓库里，每次提交前都要通过。

`CLAUDE.md` 里还有一条约定：助手发现对话已经被压缩过，就做完手头的任务、更新进度、提交，然后停下来建议你开新会话。

## 前提

1. **会话必须能直接在装有 HYSYS 的这台 Windows 机器上执行命令。** HYSYS 的 COM 接口只能在本机调用。如果助手运行在别的机器或者沙箱里，从阶段 0A 的第一步就会走不下去。
2. 仓库根目录下已经有：`CLAUDE.md`、`pyproject.toml`、`.gitignore`、`docs/REQUIREMENT.md`、`docs/MASTER_PLAN.md`、`docs/progress.md`、`docs/prompts/`、`tests/test_code_health.py`、`src/reactor_agent/__init__.py`、`evals/oracle/reference_estimates.py`。
3. 如果助手不会自动加载 `CLAUDE.md`，也不影响使用：每个阶段的提示词开头都要求先读它。
4. 助手在每个阶段都要执行大量命令（运行脚本、测试、Git）。如果每条命令都要你点一次批准，会话会被卡住。开始前把常用命令的权限放开，或者留在旁边及时批准。

## 怎么开始一个阶段

新开一个会话，发这一句话（把文件名换成对应的阶段）：

```
阅读 docs/prompts/phase-0a.md，按其中的要求执行。
```

有几项任务的阶段（3A、3B、4）可以只做其中一部分，在这句话后面说明即可，例如：

```
阅读 docs/prompts/phase-3a.md，只做任务 1。
```

| 3 | `phase-0c.md` | 平衡、Gibbs 反应器和固体碳都有结论，备选路线有对照 | 4 h | |

| 6 | `phase-1c.md` | 给一份规格文件，系统建模、求解、验证并留下记录（闸门 G1） | 2 h | |
| 7 | `phase-2a.md` | 给一段描述，系统判断反应器类型并说明理由 | 2.5 h | |
| 8 | `phase-2b.md` | 给一段描述，系统生成经过校验的规格 | 2.5 h | |

| 10 | `phase-3a.md` | 任务 1：系统在没见过的体系上也能跑通。任务 2 至 4：支持给定 Ka、选择性和收率、修改重跑 | 1.5 h（任务 1） | 3 h（任务 2 至 4） |
| 11 | `phase-3b.md` | 支持 PFR 和 CSTR；组分库查找；转化反应器的平衡可行性提示 | | 5 h |
| 12 | `phase-4.md` | 执行器有故障测试；自动重启；中断续跑；解读数字回查；全局预算 | | 5.5 h |
| 13 | `phase-5.md` | 评测结果、文档定稿、演示脚本 | 2.5 h | |

时间盒是上限，不是估计。必做的一列加起来是 29.5 小时。考核时限是 3 天，按每天 10 个工作小时算是 30 小时，余量很小。所以：

- 2C 结束后先录一版屏、导出会话记录，手里先有一套可以提交的交付物。
- 3A 只保证做完第一项任务（留出场景）。
- 3B 和 4 只在前面比时间盒快的情况下做。两者之间先做 3B，因为额外场景直接计分。
- 阶段 5 的时间不要被挤占。

每份提示词的末尾都写了"时间不够时的取舍"：哪些必须做完，哪些可以推后。最容易超时的是 0B（探索）、1A（把探针收敛成 Backend）、1C 和 2C（都要在真实的 HYSYS 上联调）。1A、1C、2C 的任务分成了两段，第一段做完是一个自然的停顿点，可以在这里换新会话。

## 每个阶段结束后你要做的事

1. **核对完成标准。** 助手会给一份交接报告，逐条写明通过、未通过或未验证。对标为通过的关键项，自己抽查一两条（运行一次命令，或者在 HYSYS 界面里打开生成的 `.hsc` 看一眼）。
2. **处理待决策事项。** 看 `docs/progress.md` 的"待决策"一节。助手遇到需要改变架构、降级集成方式、或者需求有歧义的情况会停下来问你。
3. **导出这次会话的记录**，放进 `docs/ai_sessions/`，文件名带上阶段（比如 `phase-1a-1.md`，同一个阶段的第二个会话是 `phase-1a-2.md`）。AI 开发记录是考核的交付物之一。助手会在进度文件里记下每个阶段的起止时间，阶段 5 用它整理开发时间线。
4. **确认提交已经推送**到远程仓库。考核会检查提交历史和时间线。

## 需要你亲自动手的事

| 时点 | 事情 |
|---|---|
| 阶段 0A | 告诉助手 LLM 的供应商、模型、密钥所在的环境变量；提供远程仓库地址；可能需要在 HYSYS 界面里手工建一个参考 Case，并告诉助手界面上选了哪些选项 |
| 阶段 0B | 在 HYSYS 界面里看一眼代码创建的反应是否正确；如果代码创建反应走不通，决定是否降级 |
| 阶段 0C | 确认对工具设计的修改建议；固体碳走不通时决定替代做法 |
| 阶段 1C | 在 HYSYS 界面里打开一份生成的 `.hsc`，确认反应器、物流和反应都在并且已求解 |
| 阶段 2C | 按 README 从头走一遍，确认能跑通；然后录第一版屏 |
| 阶段 3B | 可能需要在 HYSYS 界面里手工建一个含 PFR 和 CSTR 的参考 Case |
| 阶段 4 | 真机验证时助手会结束 HYSYS 进程，先保存你在 HYSYS 里别的工作 |
| 阶段 5 之后 | 录正式的屏，导出全部会话记录，推送仓库；把 `docs/REPORT.md` 导出成 PDF，确认不超过两页 |

## 一个会话太长了怎么办

如果一个阶段还没做完，会话已经很长，或者助手开始重复之前做过的事、偏离本阶段的范围：

1. 让它更新 `docs/progress.md` 并提交。
2. 新开一个会话，发同样的那句话。它会读进度文件，从没做完的任务接着做。

不要在同一个会话里连着做两个阶段。

## 卡住了怎么办

按约定，助手在同一个问题上换了 5 种思路仍然不通，或者超过了时间盒，会停下来问你。这时有三种处理：

- 给它线索。比如在 HYSYS 界面里看一眼实际情况，把看到的告诉它。
- 同意它提出的替代做法，并让它记进 `docs/progress.md` 的"决策日志"。
- 换一个更强的模型开新会话，发同一句话接着做。进度文件和台账里有接手所需的全部信息。0B（用代码创建反应）是不确定性最高的阶段，最可能用到这一条。

## 可以调整的地方

- **注释和 docstring 的语言。** 现在约定用中文。想改成英文，修改 `CLAUDE.md` "可读性"一节里的那一条，并把 `pyproject.toml` 里忽略的 `D403`、`D415`、`RUF001`、`RUF002`、`RUF003` 五条规则删掉。
- **阶段的粒度。** 某个阶段在你的环境里总是做不完，可以把它的任务清单从中间切开，分两个会话各做一半，两次都发同一句话。
- **优先级。** 3B 和 4 的先后对应 `MASTER_PLAN.md` 里的待确认决策 D8。
- **规模上限。** 文件 300 行、函数 40 行、`harness/` 600 行、嵌套 3 层，这几个上限写在 `tests/test_code_health.py` 的开头。它们是给助手的硬约束，助手自己不会改；你认为需要调整时由你来改。
- **lint 规则。** 助手认为某条规则在某处让代码变差时，会加一处带原因的忽略，并在 `docs/progress.md` 的"待决策"里记一条，由你决定要不要调整规则。
