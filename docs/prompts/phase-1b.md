# 阶段 1B：规格、Recipe、结果验证

本文件是 `docs/prompts/phase-1b.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

系统的核心设计是：LLM 只负责写出一份结构化的规格（建什么），代码负责把规格变成 HYSYS 里的模型并判断结果对不对（怎么建、建成没有、算对没有）。上一个会话（1A）做好了最底层：一组有契约、幂等的工具，和它们背后的 HYSYS Backend。

这个会话做"规格"和"判断对不对"这两块，它们有一个共同点：全部是纯逻辑，不碰 HYSYS，也不涉及 LLM。具体是三样东西：

- `ModelSpec`：一份规格长什么样。
- Recipe：每种反应器类型，怎么把规格编译成一串工具调用。
- 验证：拿到 HYSYS 读回的结果之后，怎么判断它是对的。

把它们串起来真正执行，是下一个会话（1C）的事。

## 本阶段的目标

会话结束时：

1. 三个考核场景各有一份手写的规格文件，能被加载并通过校验。
2. 每份规格能被对应的 Recipe 编译成一份建模计划，计划里每一步的工具名和入参都是对的。
3. 有一组验证检查和指标计算函数。给它们一份正确的结果，全部通过；给它们一份有某种错误的结果，对应的检查失败。

以上三点都由不需要 HYSYS 的单元测试证明。

## 要建的模块

```
src/reactor_agent/
├── spec/
│   ├── model_spec.py     规格模型，以及从文件加载规格
│   ├── components.py     组分表的模型和加载，分子式解析
│   ├── plan.py           BuildPlan 和其中的步骤
│   └── results.py        Issue、CheckResult、NormalizedResult、任务终态的枚举
```

数据模型都放在 `spec/`，`recipes/` 和 `validation/` 里只有逻辑。这样下一阶段的状态和 Trace 可以保存和显示计划、检查结果，而不需要导入 `recipes/` 和 `validation/`。

## 任务

### 1. ModelSpec

`spec/model_spec.py`：描述"要建一个什么样的反应器模型"。它是"代码已经接受的规格"，所以里面没有待换算的单位，也没有歧义。它是后面所有阶段的地基，字段和取舍按下表来。名字可以调整，结构不要变。

| 字段 | 内容 | 说明 |
|---|---|---|
| 反应器类型 | 1A 定义的五种之一 | PFR 和 CSTR 暂时没有 Recipe |
| 物性包 | 枚举，复用 1A 在工具入参里定义的那个 | 只列台账里验证过的 |
| 组分 | HYSYS 规范名的序列 | Gibbs 反应器的候选产物也列在这里 |
| 进料 | 一股或多股。每股有名字、温度（°C）、压力（bar，绝压）、流量、组成 | 名字只是规格里的标签；HYSYS 里的对象名由 Recipe 按顺序生成。流量是摩尔流量（kmol/h）或质量流量（kg/h），二选一。组成一律是摩尔分率，和为 1 |
| 反应 | 按类型区分的联合：转化反应、平衡反应 | 计量系数里反应物为负、产物为正，可以是分数。转化反应带基准组分和转化率（%）。平衡反应带 Keq 来源。Gibbs 反应器没有反应 |
| 压降 | bar | 必填。取了默认值要有对应的假设条目 |
| 热模式 | 枚举，复用 1A 定义的：绝热、规定出口温度 | 只列台账里验证过的。验证过"规定热负荷"的话也加上 |
| 工况 | 至少一个。每个工况有名字，以及它要设定的值 | 热模式是"规定出口温度"时，出口温度写在工况里，每个工况都要有。顶层只有热模式，没有具体的温度 |
| 待求指标 | 按类型区分的联合 | 见任务 5 |
| 假设 | 编号、针对的字段、取值、理由 | "针对的字段"用规格里的字段路径表示，写法固定，例如 `feeds[0].mass_flow_kg_h`、`pressure_drop_bar`。后面的报告靠它判断哪些量是假设，所以要有一个函数回答"某个字段是不是假设"，并有测试 |
| 规格哈希 | 计算得出，不是输入 | 对按键排序的规范化 JSON 取 sha256。写成 `spec/model_spec.py` 里的一个普通函数，不要做成模型的计算字段，那种写法过不了类型检查 |

其他要求：

- 冻结，序列字段用 `tuple`，物理量带单位后缀。
- 模型校验负责通用的一致性：反应和指标里出现的组分必须在组分表里；分率之和为 1；两种流量恰好给了一种；数值范围合法（温度高于绝对零度，压力和流量为正，转化率在 0 到 100 之间）；工况与热模式匹配；工况的名字不重复。随反应器类型变化的要求不放在这里，放在 Recipe 的规则里。
- 提供一个从文件加载规格的函数，YAML 和 JSON 都能读。下一阶段的命令行要用它读规格文件，也要用它读系统自己保存下来的规格。文件不存在、内容非法时抛领域错误（`E_IO`、`E_SCHEMA`），消息里说清楚哪个字段错在哪里。

### 2. 组分表

`config/components.yaml`：只登记台账"组分规范名"一节里有实测名字的组分，也就是三个场景用到的十一个。凭记忆写的规范名在 HYSYS 里很可能对不上，其余组分留给后面需要它们的阶段去加并且实测。

每个组分有：HYSYS 规范名、中文和英文别名、分子式、分子量、常温常压下的相态（气、液、固）。

`spec/components.py`：组分表的模型、加载函数，以及一个把分子式变成"元素 → 原子数"的小函数，供元素守恒检查使用。文件路径由调用方传入，这里不猜路径。

### 3. 三份规格文件

`evals/golden_specs/` 下三份 YAML，数值取自计划 §17 的三个小节，包括那里列出的假设。场景的名字只出现在 `evals/` 里。

- 组成写成摩尔分率，位数写足，使它们的和在 1e-6 之内等于 1。由配比或质量分率换算来的，把换算过程写在 YAML 的注释里。
- 固体碳那个场景的建模方式（一股进料还是两股，是否两段）以台账的结论和我的确认为准。

### 4. 计划和 Recipe

`spec/results.py` 里先定义 `Issue`，Recipe 的规则和阶段 2B 的规格校验都用它。它有四个字段：错误码、字段路径、给人和 LLM 看的说明、这个问题是不是出在用户给的信息上。

`spec/plan.py`：`BuildPlan` 是一串有序的步骤。每一步有编号、工具名（1A 的枚举）、入参模型，并标明它属于 Basis 阶段、流程图阶段，还是某个工况。计划自身的一致性在模型校验里完成：Basis 阶段的步骤只能用 `basis.*` 的工具，流程图阶段只能用 `flowsheet.ensure_*`，工况的步骤只能用 `flowsheet.set_spec`。

计划里只有建模步骤。连接 HYSYS、新建 Case、求解、读快照、保存，是每种反应器都一样的动作，由下一阶段的执行器直接调用，不进计划。

`recipes/base.py`：Recipe 的接口和注册表。接口有三个方法：

| 方法 | 输入 | 输出 | 做什么 |
|---|---|---|---|
| 规则 | 规格、组分表 | 问题清单（`Issue` 的序列，没有问题就是空的） | 这种反应器类型对规格的要求。比如转化反应器至少要有一个转化反应、不能有平衡反应；同一个基准组分的并行转化率之和不超过 100；Gibbs 反应器不需要反应，但组分表要覆盖进料里的每一种元素（用分子式判断） |
| 编译 | 规格 | `BuildPlan` | 这种反应器需要哪些对象、按什么顺序建、各自的入参是什么 |
| 专有检查 | 规格、工况、快照 | 检查结果的序列 | 只有这种反应器才有的结果检查。比如转化反应器：基准组分实际的转化率等于设定值（±0.1 个百分点） |

计划 §23.2 的接口示例是这三个方法。派生指标不在 Recipe 里，它由规格里的指标请求驱动，统一在 `validation/metrics.py` 计算。

每种反应器类型一个实现，登记在一个以反应器类型为键的注册表里。查不到时注册表返回 `None`，由调用方决定怎么办。

Recipe 是纯函数：不做 I/O，不碰 Backend，不知道 HYSYS 的存在。几点具体要求：

- 建模顺序以台账的调用序列和计划 §17 的三张"HYSYS 构建计划"表为准。表里头两步（`session.connect`、`case.ensure`）和工况里的求解、读取不属于计划。台账里确认过的工具调整优先。
- 对象的名字（进料、出料、能流、反应、反应集、反应器）由 Recipe 按计划 §9.5 的约定生成。有多股进料时按顺序编号（`Feed`、`Feed-2`……）。
- 工况的步骤只包含改规定值的调用，不包含创建对象的调用。
- 如果台账的结论是 HYSYS 不接受分数计量系数，由转化反应器的 Recipe 在编译时把带分数系数的反应拆成几个并行的反应，并算出各自的转化率。`ModelSpec` 不因此改变。

### 5. 结果验证

数据模型在 `spec/results.py`，逻辑在 `validation/`。

**检查。** `validation/checks.py`：计划 §12.3 的 V1 至 V7，每项一个小函数。检查函数需要的输入不止规格和快照：还要当前工况（出口温度的目标在工况里）、计划（期望有哪些对象、叫什么名字）、组分表（分子式）。把这些收在一个冻结的上下文对象里，每个检查函数的签名都是"上下文 → 检查结果"。检查结果包含：编号、是否通过、级别（致命或警告）、期望值、实测值、一句说明。

- V1 只看求解状态。某个量有没有值归 V5。
- V2 需要的期望对象从计划里取，不要在验证层重新实现一遍命名规则。
- V7 的守恒计算要包含所有进料和所有出料。固体从哪股出料离开，以台账为准。
- 各反应器类型的专有检查在 Recipe 里，通用检查在这里。

**指标。** `validation/metrics.py`：按规格里的指标请求，从快照计算。指标请求是有类型的，本阶段有三种：

| 指标 | 定义 |
|---|---|
| 转化率 | 某组分：（进料量 − 出料量）÷ 进料量。进料和出料都按全部物流合计 |
| 收率 | 某产物相对某基准组分：产物的出料摩尔流量 ÷ 基准组分的进料摩尔流量。不乘计量系数 |
| 比值 | 两个组分的出料摩尔流量之比 |

定义要写进指标的结果里，报告会把它展示给用户。分母为零或者用到的量是 `None` 时，指标的值是"无"，不要让它参与算术，也不要抛异常。

"某个组分在全部进料或全部出料里的总量"这类计算，Recipe 的专有检查也要用（比如核对实际的转化率）。`recipes` 不能导入 `validation`，所以把这几个纯函数放在 `spec/` 里，两边共用，不要各写一遍。

**结果。** `validation/normalized.py` 提供两个函数：

- 组装一个工况的结果（`NormalizedResult`）：每股出料的温度、压力、摩尔流量、质量流量、各组分的摩尔分率和摩尔流量；气相出料扣除水之后的干基摩尔分率（出料不含水时与湿基相同）；反应器的热负荷；各项指标；全部检查结果；假设清单；出处（HYSYS 版本、Case 文件、时间、规格哈希）。干基组成总是给出，不需要用户请求，报告会直接用它。计划 §12.3 的 V8（规格请求的每项指标都算出了值）在这里判断，作为一条检查结果放进去。
- 判定任务的结局：返回值是任务终态的枚举。这个枚举定义在 `spec/results.py`，包含全部五种终态（完成、带警告完成、失败、不支持、需要补充信息），本函数只会返回前三种，后两种由执行器在别处给出。输入是全部工况的结果，以及每个工况的 `.hsc` 是否已经保存。规则见计划 §7.5：有任何致命检查失败、有工况没有结果、或者文件没有保存，是失败；只有警告级的检查没通过，是带警告完成；否则是完成。§7.5 的第 4 条（报告已生成）本阶段不涉及，阶段 2C 再加。

### 6. 测试

这个会话的全部代码都应该有单元测试，而且都不需要 HYSYS。

- **ModelSpec**：三份规格文件能加载；规格导出成 JSON 再加载回来，哈希不变；每条一致性规则有一个违反它的用例；加载不存在的文件和非法的内容，得到带错误码的领域错误。
- **Recipe**：对每种类型，断言编译出的步骤顺序、工具名和关键入参；多工况的规格编译出对应数量的工况步骤；每条专有规则有一个违反它的用例；注册表查不到的类型返回 `None`。
- **检查**：手工构造一份正确的快照（做成 `tests/conftest.py` 里的 fixture，下一阶段的执行器测试要复用它），全部通过。然后每次改坏一个地方，断言失败的检查集合与预期的一致。一处破坏可能让不止一项检查失败（比如一个量未知会同时影响 V5 和 V7），所以预期写成"破坏 → 应当失败的检查集合"的表。要覆盖的破坏：缺一个对象、组成之和不是 1、质量不守恒、某个元素不守恒、出口温度不等于规定、某个量未知、求解状态不是已求解。
- **指标**：用手工构造的快照（数值取精确值）和手算的期望值，按很小的容差断言。三种指标和干基组成各有用例，包括分母为零和量未知的情况。
- **结局判定**：全部通过是完成；只有警告是带警告完成；有致命失败、缺工况结果、文件没保存，各是失败。
- **分子式解析**：包括带括号和不带括号的写法，以及纯元素。

## 难点

**验证比建模更容易写错，而且错了不容易发现。** 检查函数如果写得宽松，错误的模型也会"通过"，系统会把错误的结果当作正确的报告给用户。所以每项检查都必须有一个让它失败的测试。

**不要让三个场景渗进 `src/`。** Recipe 按反应器类型写，不按场景写。判断标准：换一个同类型的反应体系，Recipe 一行都不用改。三个场景的具体数值只出现在 `evals/golden_specs/` 和测试里。

**不要为还没有的需求预留字段。** `ModelSpec` 的结构要浅，能用枚举的地方不用字符串。上表之外的字段，等到需要它的阶段再加。

**快照里有 `None`。** HYSYS 没有算出来的量在快照里是 `None`。检查函数和指标函数要明确处理它：该报"未知"的报未知，不要让 `None` 参与算术。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- 每项检查是一个独立的小函数，签名相同，放在一张表里依次执行，没有一个什么都查的大函数。
- `ModelSpec` 的校验和 Recipe 的规则没有重复：通用的在模型里，随类型变化的在 Recipe 里。
- 三个 Recipe 之间相同的步骤（建物性包、建进料、建出料）只写了一次。
- `src/` 里搜不到三个场景的组分名和数值；它们只在 `config/`、`evals/` 和 `tests/` 里。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。

## 本阶段不做

- 不做执行器、状态、Trace、命令行，那是阶段 1C。
- 不运行 HYSYS。
- 不做 LLM 相关的任何东西，不做 `TaskSpec` 和单位换算（阶段 2B）。
- 不做 V9 的参照值比对。
- 不往组分表里加没有实测规范名的组分。

## 完成标准

1. `ruff format --check .`、`ruff check .`、`mypy src`、`pytest` 全部通过，其中包括 `tests/test_code_health.py`。
2. 三份规格文件加载成功，各自编译出的计划与计划 §17 对应的构建表一致（去掉头两步；台账里确认过的调整优先）。
3. V1 至 V8 每项检查各有一个通过的测试和一个失败的测试。
4. 三种指标和干基组成的测试通过。
5. 交接报告里有 `python tests/test_code_health.py` 的输出，以及按 `CLAUDE.md` 做代码体检的发现和处理结果。
6. `docs/progress.md` 已更新，改动已分多次提交。

时间盒大约 2.5 小时。

时间不够时的取舍：能推后的只有这里列出的功能，质量闸门和收尾的代码体检不在其中。按"规格 → Recipe → 验证"的顺序做，做完一块提交一块。到时间还没做完，就停在一块完整的地方，把没做的写进进度文件。不要为了赶时间而省掉检查的失败用例。

## 交接

按 `CLAUDE.md` 的格式给出交接报告。另外列出：`ModelSpec` 的字段清单；`BuildPlan` 和 Recipe 接口的定义；下一阶段的执行器需要调用的函数（加载规格、取 Recipe、检查、指标、组装结果、判定结局）及其签名。
