# 阶段 2B：把用户的描述变成规格

本文件是 `docs/prompts/phase-2b.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

现在系统已经有两段：2A 做的选型（描述 → 反应器类型），和 1B、1C 做的建模（规格文件 → HYSYS 里经过验证的结果）。这个会话把中间接上：让 LLM 根据用户的描述和选型结论写出规格，再由代码把它校验、换算成执行器能直接执行的 `ModelSpec`。

这里有一条贯穿全项目的界线，这个会话把它落成代码：

- **LLM 写 `TaskSpec`。** 它记录"用户说了什么"：数值和单位照原文抄，配比照原文抄，缺的信息声明缺失或者给出带理由的假设。LLM 不做任何换算和算术。
- **代码产出 `ModelSpec`。** 单位换算、配比归一化、组分名解析、守恒检查、自由度检查，全部由代码做。通过了才冻结成 `ModelSpec`；通不过，把问题清单交回给 LLM 重写。

这样划分是因为 LLM 的换算和算术不可靠，而且出了错很难发现。

## 本阶段的目标

执行

```
reactor-agent run --text-file <一段反应过程描述.txt> --dry-run
```

系统依次输出选型结论、换算后的规格、假设清单、将要执行的建模步骤，不触碰 HYSYS。对三个考核场景的输入，得到的规格在"用户明确给出的量"上与 `evals/golden_specs/` 里的手写规格一致。

## 任务

### 1. TaskSpec

`spec/task_spec.py`：LLM 要填写的结构。它的形状决定了 LLM 填得对不对，所以要浅，每个字段的含义要单一。

- 每个物理量由三部分组成：数值、单位（原文里的写法）、来源（用户给出，或者假设）。来源是假设时必须带理由。
- 压力另带一个基准：绝压、表压，或者原文没有说明。
- 进料是一个列表，可以有多股。
- 组成带基准（摩尔或质量）和各组分的原始数值，可以是配比，不要求归一化。可以指定一个"余量"组分，它的份额由代码算。原文说"浓度 62%，其余是水"时，LLM 不需要自己算出 38。
- 组分用 LLM 认识的名字（常用英文名或分子式），不要求是 HYSYS 的规范名。
- 反应带计量系数。一个产物可以拆给几个组分，各带一个配比（不要求归一化），代码按配比把系数分下去。这用来表达"产物是几种异构体"这类情况。转化反应带基准组分和转化率；平衡反应带 Keq 来源。
- 反应器类型取自选型结论，LLM 不能改。按反应器类型做成可区分的联合，每种类型只包含它需要的字段。
- 工况、待求指标、假设清单、歧义清单、缺失信息清单。缺失信息的每一条写明缺的是哪个字段，这样代码能判断它是不是可以假设的量。

每个字段的说明（pydantic 的 `description`）会成为提示的一部分，要写得准确、简短，并说明"照原文抄，不要换算"这类约束。

### 2. 规范化

`config/units.yaml` 和 `spec/normalize.py`：把 `TaskSpec` 变成 `ModelSpec`，或者变成一份问题清单（1B 定义的 `Issue`）。全部是纯函数。

- **单位换算**到规范单位（°C、bar 绝压、kmol/h、kg/h）。单位表要覆盖原文里常见的写法：度、摄氏度、℃、°C、K；bar、MPa、kPa、atm；kmol/h、kg/h、t/h、Nm3/h、Nm³/h。标准体积流量按 0 °C、101.325 kPa 下 22.414 Nm³/kmol 换算成摩尔流量。表压换算成绝压。不认识的单位是一个问题，不要猜。
- **组分名解析**：通过 `config/components.yaml` 的别名表换成 HYSYS 规范名，大小写不敏感。解析不了的组分是一个问题，问题里带上名字最接近的几个候选。
- **组成归一化**：算出余量组分的份额；配比变成分率；质量基准用分子量换成摩尔分率。`ModelSpec` 里的组成只有摩尔分率。
- **产物配比**：把拆给几个组分的产物系数按配比分下去。
- **默认值**：只有下表里"可以假设"的字段可以取默认值。默认值通过同一个函数写入，这个函数同时登记一条假设，这样从结构上保证不存在没有登记的默认值。
- `ModelSpec` 自身校验没通过时，把 pydantic 的错误转成问题清单，不要让异常直接抛出去。

问题清单里的每一条是 1B 定义的 `Issue`：错误码、字段路径、给 LLM 看的说明、问题是不是出在用户给的信息上。错误码只用三个：结构和单位的问题是 `E_SCHEMA`，组分名解析不了是 `E_COMPONENT_NOT_FOUND`，其余业务规则的问题是 `E_RULE`。

哪些量可以假设，哪些不可以：

| | 字段 | 处理 |
|---|---|---|
| 可以假设 | 流量（题面允许自定，或者没有给） | LLM 给出取值和依据；它只影响流量和热负荷的绝对值 |
| | 压力是绝压还是表压（原文没有说明） | 默认绝压 |
| | 进料压力（原文只给了一个压力，比如操作压力或出口压力） | 进料压力取这个值 |
| | 压降 | 默认 0 |
| | 热模式（没有给出口温度，也没有给热负荷） | 默认绝热 |
| | 物性包 | 默认 Peng-Robinson。白名单里目前只有台账验证过的这一个 |
| | Keq 来源（没有给平衡常数） | 默认由 Gibbs 自由能计算 |
| | 产物在几种组分之间的分配（原文没有给） | LLM 给出取值和依据 |
| 不可以假设 | 进料的温度、压力、组成 | 缺了就是缺少关键信息 |
| | 转化反应器的转化率 | 同上 |
| | 用户给出的任何数值 | 即使它不合理也保持原值，作为问题报告 |

LLM 把不可以假设的量填成了"假设"时，规范化要把它作为一个问题报出来，不能放行。否则系统会对一段信息不全的描述编出一个模型。

### 3. 业务规则

`spec/rules.py`：计划 §9.4 列的十条规则里，`ModelSpec` 自身的校验还没有覆盖的那些。重点是：每个反应元素守恒（用组分表的分子式）；气体体积单位用于含固体或液体的进料时登记一条歧义假设（用组分表里的相态）；每个取了默认值的字段都有对应的假设条目。

各反应器类型的专有规则是 Recipe 的 `rules`。它由 VALIDATE 的处理函数调用，不由 `spec/rules.py` 调用：`spec` 不能依赖 `recipes`。

### 4. 建模 Skill

`skills/reactor-modeling/`：

- `SKILL.md`：写 `TaskSpec` 的通用约定。
- `references/conversion.md`、`equilibrium.md`、`gibbs.md`：每种反应器类型各自的建模要点。运行时只加载选中类型的那一份。

通用约定至少包括下面这些。它们都是一般性的，不针对任何一个场景：

- 数值和单位照原文抄，不换算，不做算术。
- 用户给出的值即使不合理也保持原值，把疑问写进歧义清单，不要替用户改成合理的值。
- 上表里可以假设的量，给出取值和依据；不可以假设的量缺了，列进缺失信息清单。
- 用户提到的物料不是纯物质时，用最接近的纯组分或组分组合代表它，并登记假设。
- 只建用户给出的进料，不添加用户没有提到的物料。按题面建模与这类过程的通常做法有明显出入时，照题面建，并登记一条假设把出入说清楚。
- 用户要的结果（转化率、收率、某两个组分的比值）写成待求指标。用户对指标给了定义的，按用户的定义。出料的湿基和干基组成总是会给出，不需要写成指标。

每份参考文件写的是这一类反应器的通用知识。举例说明界线在哪里：

- 可以写："Gibbs 反应器不需要定义反应。要考虑的副反应通过候选产物组分体现，把可能生成的组分都列进组分表。"
- 可以写："产物是几种组分而用户没有给出它们之间的比例时（比如几种异构体），采用反应温度下的热力学平衡分布，在假设里写明取值和依据。"
- 不可以写某个具体体系的进料量、分配比数值或者组分清单。

上下文里还要给 LLM 一份组分命名参考，由代码从 `config/components.yaml` 生成（组分表里已有哪些组分、可以怎么称呼），不要手写。

`CLAUDE.md` 的第 4 条不变量和 2A 写的 Skill 内容测试对这个 Skill 同样适用。

### 5. SPECIFY 和 VALIDATE

在执行器的状态表里加两个状态。处理函数只做编排。

- SPECIFY：组装上下文（系统提示、Skill 正文、选中类型的参考文件、组分命名参考、用户原文、选型结论）→ 调 LLM 得到 `TaskSpec` → 保存到 `artifacts/task_spec.json`。重写时，上下文里加上上一次的 `TaskSpec` 和问题清单，并要求只改有问题的部分。
- VALIDATE：规范化 → 通用业务规则 → Recipe 的专有规则。全部通过就冻结 `ModelSpec`，保存到 `artifacts/model_spec.json`，进入 PLAN。

VALIDATE 没通过时：

- `TaskSpec` 的缺失信息清单里有不可以假设的量：重写也变不出信息，直接以 `NEEDS_INPUT` 结束，向用户列出缺什么。
- 其他情况：带着问题清单回到 SPECIFY，最多重写 2 轮。这个上限写进 `harness/budgets.py`。
- 2 轮之后还有问题：剩下的问题里有出在用户给的信息上的（数值超出范围、写出的反应式不守恒、单位不认识、组分认不出），终态是 `NEEDS_INPUT`，说明哪里需要用户确认；否则是 `FAILED`。

问题清单和重写的轮次记进 Trace。

文本输入必须调用 LLM。没有配置密钥，或者用户加了 `--no-llm`（阶段 2C 会加这个选项）时，文本输入直接报错并返回非 0 的退出码，不要悄悄降级。

`--dry-run` 现在在 PLAN 之后停下，打印选型结论、规格摘要、假设清单、建模步骤。去掉 2A 留下的"在 SELECT 之后停下"。不带 `--dry-run` 时流程会接着进入建模；这条完整路径的联调留给 2C，本阶段不需要运行它。

### 6. 评测

在 2A 的评测用例里补上期望的参数，扩展 `evals/run_evals.py`。

三个原文场景：期望的参数直接写在用例里，格式见计划 §15.2，只列两类内容。

- 用户明确给出的量：进料的温度、压力、给定的流量、组成；转化率；反应的计量系数；工况；待求指标。比较前把组成换成摩尔分率，数值的相对容差 1e-3。
- 必须被登记为假设的字段。这些字段不比较数值，只检查它们确实在假设清单里。被假设覆盖的计量系数（比如几种异构体之间的分配）只比较它们的和。

这些期望值与 `evals/golden_specs/` 里的手写规格在用户给出的量上应当一致。三个场景各运行 3 次。

病态输入（计划 §15.3 的 L1-X1 至 L1-X4：缺温度或压力、计量式不守恒、转化率超过 100%、不存在的组分）：这四个用例文件由这个会话来写，放在 `evals/cases/` 下。和 2A 一样，它们用的体系不能与留出场景重合（乙醇脱水、合成氨、甲烷与空气燃烧）。各运行 1 次，通过的条件是两条都满足：

- 第一次校验的问题清单里出现了期望的问题（错误码和字段）。
- 最终没有把用户给的值悄悄改掉：终态是 `NEEDS_INPUT` 或 `FAILED`，并且给出的原因是对的。

### 7. 测试

- 规范化：每类换算至少一个用例，并且包含下面这几个具体的数。提示词里写的是舍入后的值，断言时给出相应的容差：
  - 摩尔比 1 : 2.7 归一化为 0.2703 和 0.7297
  - 2.5 MPa 换算为 25 bar；1.0 MPa 表压换算为 11.013 bar
  - 80000 Nm³/h 换算为 3569.2 kmol/h
  - 碳的质量分率 0.62、水为余量，换算为摩尔分率 0.7099 和 0.2901
  - 系数为 1 的产物按 24 : 52 : 24 拆给三个组分，得到 0.24、0.52、0.24
- 业务规则：每条规则一个通过的用例和一个不通过的用例。
- 默认值：每个可以假设的字段取默认值之后，假设清单里有对应的条目。
- VALIDATE 的回路：用 LLM 桩覆盖一次通过、重写后通过、两轮后仍不通过（分别得到 `NEEDS_INPUT` 和 `FAILED`）、缺少关键信息时不重写直接结束这几条路径。

## 难点

**`TaskSpec` 的结构决定了 LLM 填得对不对。** 结构越深、可选字段越多，出错越多。先写出最简单的能表达三个场景的结构，再看够不够用。字段说明比字段数量重要。

**假设和缺失的界线。** 太爱假设，系统会对一段信息不全的描述编出一个模型；太爱报缺失，三个场景都跑不通。任务 2 里那张表是这条线，Skill 里要讲清楚。

**评测没达标时怎么改。** 和 2A 一样：只改一般性的约定，不加针对某个用例的措辞，每次修改记进进度文件。三个场景需要的那几条假设（自定的流量、压力基准、产物分配、绝热、把非纯物质当作纯组分、按题面建模与通常做法的出入、标准体积流量的理解），都应当能由任务 4 的通用约定和代码里的默认值自然得到。如果你发现必须把某个场景的内容写进 Skill 才能得到它们，停下来告诉我。

**组分名。** LLM 给的名字五花八门（"H2"、"Hydrogen"、"氢气"）。别名表要覆盖这些写法。解析不了时给候选，让重写那一轮有据可依。

**依赖方向。** `spec/normalize.py` 和 `spec/rules.py` 不能导入 `recipes`、`llm`、`harness`。需要 Recipe 的地方由 VALIDATE 的处理函数来调。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- 换算、归一化、产物拆分各是独立的小函数，一个函数只做一类换算。
- 可以假设的字段取默认值，只经过"写入并登记假设"的那一个函数。
- SPECIFY 和 VALIDATE 的处理函数里没有换算和规则判断。
- `spec/normalize.py` 要做的事很多，一个文件很可能超过行数上限。动手之前在进度文件里写出 `spec/` 下新文件的划分和估计行数。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。
