# 阶段 1C：执行器、状态、Trace、命令行（闸门 G1）

本文件是 `docs/prompts/phase-1c.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

前两个会话已经准备好了三样零件：

- 1A：一组有契约、幂等的工具，和它们背后的 HYSYS Backend。
- 1B：规格（`ModelSpec`）、把规格编译成建模步骤的 Recipe、判断结果对不对的验证函数。

这个会话做把它们串起来的那一层：执行器。它拿到一份规格，按计划一步一步调用工具，记录每一步，出错时按固定的策略恢复，最后由代码判定任务是否完成。计划里把这一层叫 Harness。

做完之后，系统就是一个可以演示的"规格驱动的建模器"：给它一份规格文件，它在 HYSYS 里建出模型并给出验证过的结果。后面接入 LLM（阶段 2）只是在它前面加一段"把自然语言变成规格"。

## 本阶段的目标

执行

```
reactor-agent run --spec evals/golden_specs/<某一份规格>.yaml
```

系统从空白 Case 开始建模、求解每个工况、验证结果、保存 `.hsc`，在运行目录里留下完整的状态和过程记录，最后打印终态和关键结果。三份规格都是这样。

再执行

```
reactor-agent trace <task_id>
```

能看到这次任务的时间线：经过了哪些状态，每个状态调用了哪些工具，验证的结论，有没有发生过恢复。

## 执行器的设计

这一段是本阶段的核心，先理解再动手。

### 状态循环

执行器每次只推进一步：取出当前状态，在一张"状态 → 处理函数"的表里找到处理函数，执行它，得到下一个状态，保存状态并记录 Trace。再由一个很短的循环反复推进，直到进入终态。

全部的流程就是这张表。处理函数之间不互相调用，每个处理函数只做自己这个状态的事，并返回下一个状态。这样做有三个好处：阶段 2 要在前面插入选型和规格生成，只需要往表里加几行；每个处理函数可以单独测试；命令行可以在每一步之后打印进度，也可以让任务在某个状态之后停下（阶段 2 的 `--dry-run` 要用）。

本阶段的路径：

```
INIT -> PLAN -> PREFLIGHT -> BUILD_BASIS -> BUILD_FLOWSHEET -> SOLVE -> VERIFY -> REPORT -> terminal state
                                                                 ^         |
                                                                 +---------+  next operating case
```

| 状态 | 做什么 |
|---|---|
| INIT | 确认运行目录和冻结的规格已经就位，决定从哪里开始。本阶段的输入是规格文件，下一个状态是 PLAN |
| PLAN | 按规格里的反应器类型从注册表取出 Recipe，先运行它的规则，再编译出 `BuildPlan`。这种类型没有 Recipe 时，直接进入终态 `UNSUPPORTED`。规则不通过时以 `E_RULE` 中止，诊断里列出问题清单 |
| PREFLIGHT | 连接 HYSYS，在运行目录下新建一个空白 Case |
| BUILD_BASIS | 按顺序执行计划里属于 Basis 的步骤 |
| BUILD_FLOWSHEET | 按顺序执行计划里属于流程图的步骤 |
| SOLVE | 执行当前工况的步骤（只改规定值），然后求解 |
| VERIFY | 读回快照，把 Case 另存一份以工况命名的 `.hsc`，运行通用检查和 Recipe 的专有检查，计算指标，组装这个工况的结果。有致命检查失败时走恢复；否则，还有下一个工况就回到 SOLVE，没有就进入 REPORT |
| REPORT | 写 `result.json`，调用 1B 的判定函数得出终态。阶段 2C 会在这里加上报告的渲染 |

终态只由判定函数给出：每个工况都有结果并且没有致命检查失败，每个工况的 `.hsc` 都已保存，是 `COMPLETE`；满足这些但有警告级的检查没通过，是 `COMPLETE_WITH_WARNINGS`；否则是 `FAILED`。执行器里没有任何绕过它直接写入完成的路径。

### 出错时怎么办

工具失败时会返回带错误码的结果。执行器不自己想办法，而是查一张"错误码 → 策略"的表，得到三种动作之一：

| 动作 | 含义 | 上限 |
|---|---|---|
| 重试 | 原样再执行当前这一步。工具是幂等的，所以重试是安全的 | 见下表 |
| 干净重建 | 关闭当前的 Case，不保存；换一个新的文件名，回到 PREFLIGHT，从计划的第一步重新执行 | 每个任务 1 次 |
| 中止 | 终态 `FAILED`，并给出诊断 | |

策略表（计划 §13.2 在本阶段的子集）：

| 错误码 | 策略 |
|---|---|
| `E_NOT_FOUND`、`E_READBACK_MISMATCH`、`E_ATTACH_FAILED`、`E_CONNECT_FAILED`、`E_IO`、`E_CASE_OPEN` | 重试最多 2 次 → 干净重建 → 中止 |
| `E_TIMEOUT`、`E_NOT_CONVERGED`、`E_VALIDATION_FATAL` | 重试 1 次 → 干净重建 → 中止 |
| `E_CONFLICT`、`E_BASIS_LOCKED` | 干净重建 → 中止 |
| 其余全部 | 中止 |

几点说明：

- 计划 §13.2 是完整设计。其中的 R1（重启会话）、R3（让 LLM 重写规格）、R4（向用户提问）本阶段都没有，所以会话失效、规格本身的问题、模型缺少规定这几类在本阶段都是直接中止。
- `E_VALIDATION_FATAL` 不是工具返回的。它由 VERIFY 的处理函数在发现致命检查失败时提出，"重试"在这里的意思是重新读取快照再检查一遍。
- 没有 Recipe 而进入 `UNSUPPORTED` 不经过这张表，它不是故障。
- 干净重建而不是局部修补，是因为这类模型从头建一遍只要十几次调用、几秒钟，重建比判断"哪里坏了、怎么修"可靠得多。
- 无论走到恢复的哪一级，验证没有通过的结果都不可能得到完成的终态。

四个要调用工具的处理函数共用一个调用入口：它调用工具，失败时向恢复策略要一个决定并照着执行。不要在每个处理函数里各写一遍 `try/except` 和计数。

计数的口径：重试按步骤计，这一步成功之后清零；重建按任务计，整个任务只有 1 次。重建之后一切从头来：计划的游标、各步的重试计数、工况的序号都回到起点，已经算完的工况也重新算，因为它们的结果属于被丢弃的那个 Case。

诊断要让人不看代码就知道发生了什么、接下来该做什么：停在哪个状态、哪一步（工具名和入参）、错误码和消息、已经重试和重建了几次、Trace 和 Case 文件在哪里。几种情况要多给一点信息：

- 模型没有解出来时，带上工具返回的各对象状态（哪个对象缺什么规定）。这是定位问题最直接的线索。
- 会话失效时，给出用同一份规格重跑的命令。
- 中止时尽量把当前的 Case 存下来供检查。保存本身失败就算了，不要让它盖住原来的错误。

任务分两段。第一段不需要 HYSYS；第二段在真实的 HYSYS 上验收。第一段做完后更新进度并提交。如果这时会话已经很长，停下来告诉我，第二段在新会话里做。

### 第一段：执行器

#### 1. 任务状态和存储

`state/models.py`：`TaskState`，记录一个任务的进展。字段参考计划 §10.2，只保留现在有来源的：

- 任务标识、输入（规格文件的路径）、当前状态
- 规格哈希
- 每一步的执行记录：步骤编号、工具名、状态、尝试次数、结果状态
- HYSYS 会话和 Case 的信息：版本、进程号、当前 Case 文件
- 当前工况的序号，重试和重建的计数
- 每个工况的摘要：名字、致命和警告级的失败数、`.hsc` 的路径
- 错误记录

状态文件只存摘要。完整的规格、计划、结果各自写在 `artifacts/` 下的文件里，不在状态文件里再存一份。续跑用的字段（`run_id`、检查点列表）和 LLM 产物的字段现在不加，用到的阶段再加。

`state/store.py`：把 `TaskState` 写到运行目录的 `state.json`，以及读回来。写入必须是原子的：先写同目录下的临时文件，再替换正式文件，这样进程在任何时刻被中断，状态文件都是完整的。

`TaskState` 是全系统唯一一份会被不断更新的数据，所以要让修改它的地方尽量少：只有执行器写它，并且通过少数几个意图明确的函数来改（比如"记录一步的结果""进入下一个状态"），不要在各处直接给字段赋值。

运行目录的布局：

```
runs/<task_id>/
├── state.json            任务状态，每次状态迁移和每一步之后重写
├── trace.jsonl           事件记录，只追加
├── artifacts/
│   ├── model_spec.json   冻结的规格
│   ├── plan.json         编译出的计划
│   └── result.json       每个工况的结果和终态
└── *.hsc                 每个工况求解后的 Case
```

#### 2. Trace

`observability/trace.py`：向 `trace.jsonl` 追加事件，每行一个 JSON。事件的字段见计划 §14.1，去掉现在没有来源的（`run_id`、`skill`）。本阶段会产生的事件类型：状态迁移、工具调用、验证、检查点（保存规格、计划、Case、结果时）、恢复决策、错误。

工具调用事件通过 1A 在 `ToolExecutor` 上留的回调接入。事件要带上当前所处的状态，而 `ToolExecutor` 不知道状态；想清楚这个信息从哪里来，选最简单的做法，不要为此让 `tools/` 依赖 `harness/`。

`observability/render.py`：两个纯函数。一个把事件列表渲染成计划 §14.2 那样的时间线，同一个状态里连续调用同一个工具时合并成一行。另一个把一次失败渲染成上面说的诊断文本。它们放在这里而不是执行器里，是为了让执行器只管流程。`observability` 不能导入 `state`，所以诊断函数的入参是一个专门的小模型（定义在 `spec/results.py`），由执行器把需要的信息填进去。

#### 3. 恢复策略

`harness/recovery.py`：一个纯函数，输入错误码和已经用掉的重试、重建次数，输出下一步动作。策略是一张以错误码为键的表，不是一串条件判断。

1A 在 `errors.py` 里定义了可重试错误码的集合。两处不能打架：不在那个集合里的错误码，策略表里的重试次数必须是 0。用一个单元测试守住这一点。

`harness/budgets.py`：求解的等待上限（120 秒）、重试和重建的上限，写成具名常量。

计划 §7.3 把 RECOVER 画成了一个状态。实现时它可以只是一次函数调用加一条 Trace 事件，只要每次恢复决策都留下了记录。

#### 4. 执行器

`harness/engine.py`：上一节描述的状态表、处理函数和调用入口。

- 执行器的依赖有好几个（`ToolExecutor`、状态存储、Trace、Recipe 注册表、组分表、运行目录），后面的阶段还会加 LLM 客户端和 Skill 加载器。把它们收在一个冻结的 dataclass 里，整体传给执行器。执行器自己不创建依赖，也不导入 `backends`。
- 对外提供三样东西：创建任务（生成任务标识、建运行目录、保存冻结的规格和第一份状态文件；任务标识的格式见计划 §10.2 的示例）；把任务推进一步；一个反复推进直到终态或者到达指定状态的循环。
- 处理函数里没有按反应器类型的分支。随类型变化的东西全部来自 Recipe：规则、计划、专有检查。
- 执行计划里的步骤时，每成功一步就推进游标并保存状态。恢复动作是"重试"时，从游标处继续，自然就是重做失败的那一步。
- 传给工具的 Case 路径是绝对路径。HYSYS 是另一个进程，它不知道你的当前目录。

#### 5. 命令行

`cli.py`，用标准库的 `argparse`。入口函数是 `reactor_agent.cli:main`，`pyproject.toml` 里已经登记了 `reactor-agent` 这个命令。

- `reactor-agent run --spec <文件>`：加载规格，创建任务，运行执行器，结束时打印终态、每个工况的关键结果和指标、没有通过的检查、运行目录的位置。完成和带警告完成的退出码是 0，其他终态非 0。`--spec` 既要能读 `evals/golden_specs/` 下的 YAML，也要能读某次运行留下的 `artifacts/model_spec.json`。这样任何一次运行的规格都可以直接拿来重跑，现场演示时这是兜底手段。
- `reactor-agent trace <task_id>`：打印时间线。它同样接受 `--runs-dir`。

几个细节：

- `cli.py` 是装配点：它创建 Backend、`ToolExecutor`、状态存储、Trace 和执行器，把它们连起来。其他模块都不导入 `cli`。
- 入口写成 `main(argv: Sequence[str] | None = None) -> int`，这样测试可以在进程内调用它并检查返回值。
- 先加载并校验规格，再创建 Backend。HYSYS Backend 的导入放在装配函数里面，不放在文件顶部。这样没有 HYSYS 的机器上，"规格文件非法"这类路径照样能运行和测试。
- 项目自带的文件（`config/components.yaml`）以仓库根目录为基准定位，不依赖当前目录。运行目录默认是仓库根目录下的 `runs/`，可以用 `--runs-dir` 改。用户给的规格文件路径按当前目录解析。定位仓库根目录的代码只写一处。
- 顶层捕获领域错误，打印诊断并返回非 0 的退出码，不让用户只看到一段 traceback。
- 入口处把标准输出和标准错误设为 UTF-8。`mypy --strict` 下直接调用 `sys.stdout.reconfigure` 会报错，要先判断它是 `io.TextIOWrapper`。

报告的渲染是阶段 2C 的事。这里打印的是一份简短的结果摘要，够确认结果对不对就行。

#### 6. 第一段的测试

执行器的逻辑必须能在没有 HYSYS 的机器上测试。做法是在测试目录里写一个几十行的 `ToolExecutor` 桩：它记录收到的调用，按预先编排的脚本返回成功或者某个错误码。`model.read_snapshot` 返回的快照可以复用 1B 测试里手工构造的那份。这个桩只放在 `tests/` 里。

- **执行器**
  - 正常路径：工具被调用的顺序与计划一致，终态是完成，状态依次经过上面那条路径。
  - 多工况：每个工况各有一次改规定值、求解、读取、保存，并各有一份结果。
  - 重试：某一步先失败一次（可重试的错误）再成功，终态是完成，那一步被调用了两次。
  - 干净重建：某一步持续失败，重试用完后发生一次重建，Case 用了新的文件名，计划从头执行。
  - 上限：持续失败时，工具调用的总次数有上界，终态是 `FAILED`，诊断里有错误码。
  - 不可恢复的错误：直接中止，没有重试。会话失效时，诊断里有重跑的命令。
  - 验证失败：快照里有一处致命错误时，终态不可能是完成。
  - 没有 Recipe 的反应器类型：终态是 `UNSUPPORTED`，没有任何工具被调用。
  - 推进到指定状态后停下：任务停在那个状态，状态文件可以读回。
  - 多工况任务在第二个工况上触发重建：重建之后两个工况都重新计算，最终各有一份结果。
- **恢复策略**：用参数化测试覆盖表里的每个错误码，以及与可重试集合的一致性。
- **状态存储**：保存再读回，内容相同；写入后目录里没有残留的临时文件。
- **Trace 和渲染**：事件按顺序追加，每行是合法的 JSON；用一份手工构造的事件列表断言时间线的文本；用一个手工构造的失败断言诊断里的要素。
- **命令行**：规格文件不存在或者内容非法时，返回值非 0，输出里有可读的原因，没有 traceback。

### 第二段：在真实的 HYSYS 上验收

#### 7. 集成测试

标 `hysys`，放在 `tests/integration/`：

- 三份规格各自运行到完成，V1 至 V8 全部通过，结果与参照值的偏差在下表的范围内。
- 每份规格连续运行 3 次，三次的出料组成和流量相对偏差不超过 1e-4。
- 每次运行结束后，Case 里的对象数量与计划一致，没有多余的物流、反应或反应器。
- 干净重建：给 `ToolExecutor` 套一层测试专用的包装，在计划第一次创建进料物流之前，先用工具建一股同名但温度不同的物流，只注入一次。断言：Trace 里恰好有一条恢复事件，错误码是 `E_CONFLICT`，动作是重建；重建计数是 1；重建后的 Case 文件名与之前不同；最终 Case 里的对象数量与计划一致；终态是完成。只断言"最后完成了"是不够的，那证明不了重建发生过。

三份规格各用一种反应器，结果的容差如下：

| 规格用的反应器 | 对照 | 容差 |
|---|---|---|
| Conversion | 出料五个组分的摩尔分率，对照解析解 | 0.001 |
| Equilibrium | 两个工况出料五个组分的湿基摩尔分率，对照参照值 | 0.02 |
| Gibbs | CO 收率，对照参照值 | 落在 38% 至 42% 之间 |

解析解和参照值在计划 §17 的三个小节里。超出容差时，不要调整模型去凑数字，也不要放宽容差。先对照台账检查模型有没有建错；查不出原因，就把对比表发给我。

测试结束时关闭 Case。整个测试会话共用一个 HYSYS 连接，不要每个测试启动一次。

#### 8. 请我确认

请我在 HYSYS 界面里打开一份生成的 `.hsc`，确认反应器、物流和反应都在，并且是已求解的状态。

#### 9. 会话失效的试验

这一项放在最后做。它不是闸门 G1 的条件；时间不够时可以不做，在交接报告里写"未验证"。

在建模中途结束 HYSYS 进程，系统应当在 60 秒内以 `FAILED` 结束，诊断里说明会话已失效，并给出重跑的命令。然后照这条命令重跑一次，确认能完成。

建模只要几秒钟，手工掐时间很难。可以在 `spikes/` 里写一个一次性的脚本，用和任务 7 相同的包装方式，在第 N 次工具调用之后执行 `taskkill /F /PID <进程号>`，进程号取自 `session.connect` 的结果。这件事不要做成自动化测试，它会破坏测试会话共用的连接。把看到的输出记进进度文件。

## 难点

**主路径要保持直白。** 执行器最容易写成一个什么都管的大函数：循环、调工具、记日志、判断重试、存状态全搅在一起。判断标准是：读 `engine.py` 的人能不能在一屏之内看明白一个任务是怎么从头走到尾的。状态存储、Trace、恢复决策、诊断文本各自是独立的小模块，执行器只是调用它们。

**恢复逻辑要可测。** 把"决定做什么"（纯函数，查表）和"去做"（关 Case、换文件名、重置游标）分开。前者用参数化测试覆盖全部错误码，后者在执行器测试里覆盖。

**每条回路都要有上限。** 重试和重建的计数放在 `TaskState` 里并随状态保存。写完之后自己推一遍：在任何持续失败的情况下，工具调用的总次数都不超过"计划长度 ×（1 + 重试上限）×（1 + 重建上限）"这个量级。

**创建到一半失败的对象。** 按 1A 的约定，创建到一半失败留下的半成品，重试时会得到 `E_CONFLICT`，于是直接走干净重建。这是有意的设计，不要为了让重试生效去加清理逻辑。

**另存之后的 Case。** 每个工况求解后要另存一份 `.hsc`。另存之后 HYSYS 里活动 Case 的路径是否改变、对后续调用有没有影响，以台账里保存重开的记录为准，不要依赖没有验证过的行为。

**需要工具层没有的能力时。** 建模期间求解器是否挂起、由哪个工具负责，1A 已经按台账定了，照现状使用。如果你发现执行器需要一个现在没有的工具能力，停下来问我，不要在执行器里绕过工具层去碰 Backend。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- `engine.py` 里只有状态表、处理函数、调用工具的入口、单步推进和循环。处理函数之间不互相调用。
- 调用工具的地方只有调用入口一处；`try/except` 和重试计数不散落在各个处理函数里。
- 修改 `TaskState` 的代码集中在 `state/` 的少数几个函数里。
- 诊断文本和时间线的拼接在 `observability/render.py`，不在执行器里。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。

## 本阶段不做

- 不做 LLM 相关的任何东西，不做选型、规格生成、报告（阶段 2A 至 2C）。
- 不做自动重启会话、中断续跑、中间快照、假的 Backend、任务总时长和迁移总数的上限（阶段 4）。
- 不做任务锁和 `runs/index.jsonl` 汇总。
- 不做状态到工具组的权限白名单。执行器是唯一的工具调用方，计划自身的一致性 1B 已经在 `BuildPlan` 的校验里守住了。
- 不引入新的依赖。结束进程用 `taskkill`，不用第三方库。
- 不修改 `backends/`、`recipes/`、`validation/` 的设计。发现它们有错时，修复限于让本阶段跑通所必需的部分，并记进进度文件。
