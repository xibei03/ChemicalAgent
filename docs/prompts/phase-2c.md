# 阶段 2C：报告、端到端联调、第一版交付文档（闸门 G2）

本文件是 `docs/prompts/phase-2c.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

前面的会话已经做完了三段：选型（2A）、规格生成与校验（2B）、从规格到 HYSYS 里经过验证的结果（1B、1C）。这个会话把它们连成完整的闭环，补上最后一环——给用户的报告，然后在真实的 HYSYS 上把三个考核场景从原文跑到结果。

这是整个项目最重要的里程碑。考核的四项交付物（代码仓库、录屏、AI 开发记录、报告）是硬性要求，所以闭环一打通，就立刻产出第一版 README 和考核报告。有了可提交的版本，后面的工作都是在它之上改进。

## 本阶段的目标

执行

reactor-agent run --text-file <场景的输入.txt>

系统完成选型、规格生成、建模、求解、验证，生成一份报告。对三个考核场景的输入，终态都是完成，结果与参照值一致。同时仓库里有第一版 `README.md` 和 `docs/REPORT.md`。

## 任务

任务分两段。第一段把闭环打通（闸门 G2）；第二段写交付文档。第一段做完后更新进度并提交。如果这时会话已经很长，停下来告诉我，第二段在新会话里做。

### 第一段：报告和联调

#### 1. 报告渲染

`report/render.py`：把一次运行的结果渲染成 Markdown 报告，写到运行目录的 `artifacts/report.md`。固定六个部分（计划 §4），解读文字是另外的第七节，见任务 2：

1. 反应器类型和理由，备选类型和不选的原因。任务是从规格文件开始的、没有选型结果时，这一部分写明"反应器类型由规格文件给定"
2. 解析出的参数，以及全部假设（每条假设的取值和理由）
3. HYSYS 模型摘要：建了哪些对象
4. 每个工况的结果表（每股出料的温度、压力、流量、组成，气相出料的干基组成，热负荷）和派生指标及其定义
5. 验证结论：是否求解完成，守恒误差，规定是否满足，有没有警告
6. `.hsc` 文件的位置和运行过程摘要

要求：

- **报告里的数字全部由代码填入**，来源是代码手里已经验证过的数据：每个工况的 `NormalizedResult`、`ModelSpec`、`BuildPlan`、选型结果和运行信息。LLM 写的任何文字都不进入表格。这是为了保证用户看到的数字就是 HYSYS 算出并且通过验证的数字。
- 干基组成直接取 `NormalizedResult` 里的，渲染函数不做任何计算。
- 运行信息（任务标识、终态、文件位置、运行过程的摘要）在 `TaskState` 和 Trace 里，而 `report` 不能导入 `state`。在 `spec/results.py` 里定义一个小的运行摘要模型，由执行器填好传给渲染函数。
- 结果表要包含全部出料，含固体或液体从哪股出料离开。
- 有多个工况时，结果并排成一张对比表。
- 进料流量是假设的（假设清单里有指向它的条目）时，同时给出小时流量和按年操作 8000 小时折算的年处理量（t/a），让用户能判断这个假设是否合理。
- 每个部分一个小函数，用普通的字符串拼表格，不引入模板引擎。
- 这些规则是通用的，按"有没有多个工况""流量是不是假设"来判断，不按场景判断。

`report` 只依赖 `spec` 和 `errors`。

#### 2. 解读文字和 REPORT 状态

`skills/result-reporting/`：告诉 LLM 怎么写解读。解读回答三个问题：结果说明了什么（比如温度升高对转化率和产物分布的影响，以及原因）；哪些假设对结果影响大；结果有没有值得用户注意的地方（比如所需的热负荷很大意味着什么）。

Skill 要明确：解读可以引用报告表格里的数字，引用时照抄表格里的写法；不得出现表格里没有的数字；不下"成功"之类的结论，成功与否由验证部分给出。

REPORT 的处理函数在 1C 里只做收尾（写 `result.json`，判定终态）。现在往里加两步：

- 把每个工况的结果、选型结果、假设清单交给 LLM，得到解读文字。它在报告里单独成节，标明是由 LLM 生成的解读。LLM 调用失败时，照常生成不含解读的报告，终态不受影响。
- 用代码渲染报告并写到运行目录。给 1B 的判定函数加上计划 §7.5 的第 4 条：报告没有生成，就不是完成。代码渲染失败属于程序缺陷，按普通错误处理。

报告只在任务走到 REPORT 时生成。其他终态（失败、不支持、需要补充信息）由命令行打印诊断或者选型结论，不出报告。

加一个命令行选项 `--no-llm`：不调用 LLM，报告不含解读。`--spec` 加 `--no-llm` 是完全离线的路径，现场演示时 LLM 不可用就靠它兜底。从规格文件开始的任务在没有配置密钥时，自动按 `--no-llm` 处理并提示一句。从文本开始的任务必须用 LLM，这种情况下照 2B 的做法直接报错。

#### 3. 命令行的演示体验

#### 4. 端到端联调

用三个场景的输入（从 `evals/cases/` 里取）逐个运行完整流程。

出问题时，先用 `reactor-agent trace` 确定是哪一段的问题：选型、规格、编译、建模、求解，还是验证。然后修那一段的一般性原因。不要为了让某个场景通过而在 `src/` 或 Skill 里加针对它的处理。每个问题和修法记进进度文件的"问题与解决"。

联调满 1.5 小时还没有一个场景通过，停下来把 Trace 和你的分析发给我。

#### 5. 第一段的测试

## 难点

**解读文字和表格打架。** LLM 可能在解读里写一个和表格不一致的数字。Skill 里的约束是第一道防线；报告的版式是第二道：数字由代码渲染在表格里，解读单独成节并注明来源。自动核对解读里的数字属于阶段 4，现在不做。

**联调时的问题定位。** 完整流程有三次 LLM 调用和十几次 HYSYS 调用，出错时不要凭感觉改。先看 Trace，确定是哪一个状态、哪一步、什么错误码。

**LLM 的不稳定性。** 同一段原文多跑几次，规格可能有细微差别。用户给出的量不应该变；假设的量（自定的流量、异构体的分配等）可能变，这是允许的，但每次都要被登记为假设。完成标准里的结果对照已经考虑了这一点。

**不要回头重构。** 这个会话的重点是打通和交付。发现之前的代码有可以改进的地方，记进进度文件，除非它挡住了联调，否则不动它。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- 报告的每个部分一个小函数，渲染函数不读文件、不调 LLM、不做任何计算，只把数据排成表。
- REPORT 的处理函数只做编排：取解读、渲染、写文件、判定终态。
- 联调中的修复落在出问题的那一层，没有在上层加补丁去绕过下层的问题。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。

## 完成标准（闸门 G2 和里程碑 M1）

1. `ruff format --check .`、`ruff check .`、`mypy src`、`pytest` 全部通过，其中包括 `tests/test_code_health.py`。
2. 三个场景的输入各自执行 `reactor-agent run`，终态是 `COMPLETE`，或者是 `COMPLETE_WITH_WARNINGS` 并且每条警告你都能向我解释。致命检查全部通过，报告已生成。
3. 结果与参照值的偏差在容差内：
   - 蒸汽重整：两个工况出料五个组分的湿基摩尔分率，对照计划 §17.1 的参照值，不超过 0.02。
   - 甲苯歧化：出料中甲苯、苯、三种二甲苯合计的摩尔分率，对照 0.500、0.250、0.250，不超过 0.001。三种二甲苯各自的分率等于 0.250 乘以本次规格里的分配比，不超过 0.001。分配比是 LLM 给出的假设，每次运行可以不同，所以不与固定的数对照。
   - 水煤浆气化：CO 收率在 38% 至 42% 之间。
4. 三份报告各自包含：
   - 蒸汽重整：两个工况并排的对比表，小时流量和年处理量。
   - 甲苯歧化：三种二甲苯异构体各自的流量和分率，出口温度。
   - 水煤浆气化：CO 收率及其定义，未反应的碳量，所需的热负荷，以及"按题面没有氧气进料"这条假设。
5. 2A、2B 的评测指标没有退步。Skill 内容的测试通过。
6. `reactor-agent run --spec <文件> --no-llm` 能跑完并生成报告，这次运行的 Trace 里没有 LLM 调用事件。
7. `README.md` 和 `docs/REPORT.md` 已经写好，`docs/examples/` 里有三份报告。请我按 README 从头走一遍，确认能跑通。
8. 交接报告里有 `python tests/test_code_health.py` 的输出，以及按 `CLAUDE.md` 做代码体检的发现和处理结果。
