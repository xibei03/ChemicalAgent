# 阶段 5：最终交付

本文件是 `docs/prompts/phase-5.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。这是一个考核项目，考核包括提交交付物和现场演示。

开发已经结束。这个会话不加任何功能，只做三件事：确认系统处于可以提交的状态，把交付文档定稿，为现场演示做准备。

考核的四项交付物是：代码仓库和 README、运行录屏、AI 开发记录、一到两页的报告。评分看三方面：三个场景的通过数量和结果准确性，探索过程与系统设计，AI 协作的效率。现场演示时可能给出额外的场景，并且要回答关于设计的问题。

## 本阶段的目标

1. 一份完整的评测结果，证明系统当前的状态。
2. 代码仓库干净：质量闸门全过，没有残留的调试代码，文档与代码一致。
3. `README.md` 和 `docs/REPORT.md` 定稿。
4. 我拿到一份演示脚本和一份问答准备。

## 开始前先读

- `CLAUDE.md`、`docs/progress.md` 全文（"问题与解决""决策日志""与计划的偏差"是定稿报告的素材）
- `docs/REQUIREMENT.md` 的 §5、§6、§7
- `docs/MASTER_PLAN.md` 的 §15.6、§21、§22.1、§22.2
- `README.md`、`docs/REPORT.md` 的当前版本，`docs/HYSYS_INTEGRATION.md`

## 先确认系统现在有什么

阶段 3A 的任务 2 至 4、阶段 3B、阶段 4 都是可选的。先从进度文件里查清楚它们各自做了没有，列成一张表写进进度文件。后面的每一项任务都以这张表为准：

- 回归只跑已经实现的功能。留出用例以用例文件里写的期望终态为准。
- README 的"已知限制"列出没有做的那些（比如不支持 PFR 和 CSTR、不支持用户给定平衡常数、不支持中断续跑）。
- 演示脚本和问答准备只讲已经实现并且回归通过的功能。

## 任务

### 1. 全量回归

按顺序执行，把结果汇总进 `docs/EVAL_RESULTS.md`。选型、规格、端到端这几节由 `evals/run_evals.py` 生成（端到端的模式是阶段 3A 加的），记录模型名、Skill 版本、提交哈希、日期。质量闸门和集成测试这两节没有脚本，由你运行之后把命令和结果摘要写进去。

- 质量闸门：`ruff format --check .`、`ruff check .`、`mypy src`、`pytest`
- 需要 HYSYS 的集成测试
- 选型的评测：三个原文场景各 5 次，其余用例各 1 次。规格的评测：三个原文场景各 3 次，病态输入各 1 次
- 三个考核场景端到端连续 3 轮，共 9 次
- 留出场景端到端各 1 次
- 用规格文件回放三个场景各 1 次（`--spec` 加 `--no-llm`），过程中不调用 LLM
- 阶段 1C 的会话失效试验如果当时没有做（看进度文件），现在补做一次。期望的结果取决于阶段 4 的自动重启做了没有：做了，系统应当自己恢复并完成；没做，系统应当以失败结束并给出重跑的命令

门槛见计划 §15.6。有不达标的项，如实记录。能在一小时内找到一般性原因并修好的就修，修完重跑受影响的部分；否则把现象和你的判断告诉我，由我决定。不要为了让数字达标而放宽容差或者改用例。

### 2. 代码体检

对整个 `src/` 按 `CLAUDE.md` 的八条逐条检查，这次是全仓库范围：

- 列出所有 `# noqa` 和 `# type: ignore`（`python tests/test_code_health.py` 的输出里有），逐个判断它是不是真的属于检查工具的局限。不是的，修掉。
- 找出没有被任何地方使用的函数、参数、配置项，删掉。只被测试使用的假 Backend（如果有）不算。
- 用 `git log -p tests/test_code_health.py` 确认代码体检测试里的依赖表和行数上限从仓库建立以来没有被放宽。被放宽过的，恢复原值并修代码；进度文件的决策日志里记着是我同意改的除外。
- 在 `src/` 和 `skills/` 里搜索三个考核场景的名字和特征词（重整、歧化、水煤浆、甲苯、二甲苯，以及场景里的数值 710、13.5、10000、80000、1400 等），确认运行时代码和 Skill 里没有针对场景的处理。`config/`、`evals/`、`tests/` 里出现是正常的。
- 运行 `python tests/test_code_health.py` 得到各模块的代码行数，和 `MASTER_PLAN.md` §22.1 的规模预算对照，写进交接报告。

只修体检发现的问题，不做风格上的重写。每处修改之后质量闸门要保持通过。

### 3. 文档与代码对齐

- `docs/MASTER_PLAN.md`：不重写。在 `docs/progress.md` 的"与计划的偏差"里确认每一条偏差都有记录和原因。
- `docs/HYSYS_INTEGRATION.md`：确认接口事实表里每一项的状态都是最终状态，Backend 用到的每个调用都能在表里找到。
- 写一个小脚本（放在 `evals/` 下），生成 `docs/TOOLS.md`。内容是两张表：工具表（工具名、入参字段和类型）来自工具注册表；错误码表（错误码、是否可重试、恢复策略）来自 `errors.py` 和 `harness/recovery.py`。手写的工具文档会和代码不一致，所以用生成的。

### 4. README 定稿

在第一版的基础上更新，使它与当前的代码一致。重点检查：安装步骤能不能在一台干净的机器上照着做下来；每条示例命令都实际运行过；已知限制一节如实列出系统做不了的事（哪些反应器类型不支持，哪些输入方式不支持）和采用的假设。

### 5. 考核报告定稿

`docs/REPORT.md`，四部分：技术选型理由、系统架构、探索过程、遇到的问题及解决方式。篇幅是一到两页：正文两千字以内，加一张图和一张结果表。

写这份报告时记住读者是谁：考官读过很多份这样的报告，他们想知道的是你做了哪些判断、为什么这样判断、哪些路走不通。所以：

- 技术选型：写清楚为什么让 LLM 只写规格而不直接操作 HYSYS，以及考察过哪些与 HYSYS 通信的路线、各自的结论。
- 系统架构：一张图，加上最关键的一条边界（LLM 写规格，代码建模并判断对错）。三个场景的结果作为一张表放在这一部分的末尾：每个场景一行，写反应器类型、关键结果和采用的假设（尤其是气化场景没有氧气进料、流量单位的理解）。
- 探索过程：按时间写真实发生的事。哪个接口没有文档、怎么找到的、哪些尝试失败了。这是评分权重最高的部分之一，也是最不容易写出套话的部分，因为素材都在探索日志里。
- 问题与解决：挑最有代表性的三到四个，每个写现象、原因、解决办法。

考核的评分里有一项是 AI 协作的效率，开发速度本身也计分。从 `git log` 和进度文件里各阶段的起止时间，整理出一张开发时间线（每个阶段用了几个会话、多长时间、产出了什么），放在 README 里，并在报告的探索过程里用一两句话引用。

不要写泛泛的优点陈述。每一句话都应该有具体的事实支撑。超出篇幅就删内容。在交接报告里提醒我把它导出成 PDF 看一眼是不是在两页之内。

### 6. 演示脚本

在 `README.md` 里加一节"演示步骤"，或者在交接报告里直接给我。内容：

- 演示前的检查清单：HYSYS 能启动、许可证正常、LLM 密钥已配置、没有残留的 HYSYS 进程。
- 三个场景各自的命令、屏幕上会出现什么、大约需要多长时间、最后指给考官看报告里的哪几处。
- 一个留出场景的演示，用来说明系统不是只会三个场景。
- 一次"修改条件再算"的演示（如果这个功能已经实现）。
- 出问题时的兜底：LLM 不可用时用规格文件回放；HYSYS 卡住时怎么处理。

### 7. 问答准备

在交接报告里给我一份清单：考官最可能问的十个问题，每个问题的要点，以及答案在仓库里的什么位置。至少包括：为什么这个场景选这种反应器而不是另一种；气化场景为什么没有氧气、CO 收率为什么是这个数；LLM 判断错了会怎样；HYSYS 出错了会怎样；怎么支持一种新的反应器；哪些事情系统做不了。

## 难点

**这个阶段最大的风险是"顺手改一下"。** 回归通过之后，任何对 `src/` 的修改都可能破坏已经验证过的东西。除了体检发现的问题和回归不达标的修复，不动代码。每次改动之后重跑受影响的测试。

**报告容易写成功能清单。** 考官已经有代码和 README 了。报告要写的是代码里看不出来的东西：判断、取舍、弯路。

**如实。** 评测结果、已知限制、假设，都按实际情况写。一个清楚说明了自己边界的系统，比一个声称什么都能做的系统更可信。

## 本阶段不做

- 不加功能，不重构。
- 录屏、导出 AI 会话记录、推送到远程仓库由我来做。

## 完成标准

1. `docs/EVAL_RESULTS.md` 已生成，包含任务 1 列出的全部项目。
2. 质量闸门全部通过；三个考核场景端到端 9 次全部通过，或者不通过的情况已经如实记录并告诉了我。
3. 代码体检完成，结论和各模块行数写在交接报告里。
4. `README.md`、`docs/REPORT.md`、`docs/TOOLS.md` 已定稿。`docs/REPORT.md` 的正文在两千字以内。`docs/examples/` 里的三份报告是最新的。
5. 演示脚本和问答准备已经给我。
6. `docs/progress.md` 已更新，改动已提交。

时间盒大约 2.5 小时。回归运行的时间很长，让它在后台跑，同时写文档。

时间不够时的取舍：必须做完的是质量闸门、三个场景的 9 次端到端、`docs/EVAL_RESULTS.md`、README 和报告的定稿。可以压缩的是：`docs/TOOLS.md` 只生成工具表；问答准备压到六个必答的问题；代码体检只做忽略注释、场景词和行数三项。
