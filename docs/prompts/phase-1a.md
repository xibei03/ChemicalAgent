# 阶段 1A：Backend 和 Tool 层

本文件是 `docs/prompts/phase-1a.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

探索阶段（0A 至 0C）已经结束。三种反应器各自的 COM 调用序列、哪些接口可用、遇到同名对象和进程中断时会发生什么，都记在 `docs/HYSYS_INTEGRATION.md` 里，探针脚本在 `spikes/`。

从这个会话开始写正式代码。系统的设计是：LLM 只产出一份结构化的规格，代码把规格编译成一串工具调用，工具再通过 Backend 操作 HYSYS。这个会话做最底下的两层：把探针里验证过的 COM 调用收敛成一个 Backend，再在它上面加一层有契约的工具。上面的规格和编译（1B）、执行（1C）在后面两个会话做。

## 本阶段的目标

会话结束时，不写一行 COM 代码，只靠调用工具，就能在 HYSYS 里建出探索阶段的三个模型（转化、平衡、Gibbs）并读回正确的结果。

这两层要保证四件事，上层才能放心依赖它们：

- **契约。** 每个工具的入参和结果都是有类型的模型，非法入参在进入 HYSYS 之前就被拒绝。
- **幂等。** 同一个调用执行两次，第二次不会重复创建对象。
- **读回。** 每次写入之后立刻读回比对，写入没有生效时报错，而不是若无其事地继续。
- **隔离。** 所有 COM 细节和 COM 异常都留在 Backend 里，上层只看到领域模型和领域错误。

## 任务

任务分两段。第一段定契约，不需要 HYSYS；第二段在真实的 HYSYS 上实现。第一段做完后更新进度并提交。

### 第一段：契约

#### 1. 错误码和领域异常

`errors.py`：`ErrorCode`（`StrEnum`）和 `ReactorAgentError`。

- 把计划 §13.2 表里的错误码一次建全，后面的阶段就不用回来改这个文件。
- 异常携带错误码、给人看的消息，以及一个放细节的字段。
- "是否可重试"由错误码决定，不由抛出的地方各自指定。定义一个可重试错误码的集合作为唯一的来源：计划 §13.2 里策略链以 R0（重试、重新求解、重新读取）开头的那些错误码是可重试的，其余不是。"可重试"的含义是：原样再调用一次有可能成功。
- 两个容易混的码：`E_NOT_FOUND` 是本该存在的对象读不到；`E_COMPONENT_NOT_FOUND` 是组分名解析不了，或者 HYSYS 的组分库里没有这个组分，属于规格的问题，再试也没有用。
- `E_LLM` 不可重试。LLM 调用的重试在 LLM 客户端内部完成，执行器不再重试。

#### 2. 工具入参、结果和快照的模型

`spec/tool_args.py`、`spec/tool_results.py`、`spec/snapshot.py`，用 pydantic，全部冻结，序列字段用 `tuple`。

本阶段的工具有 12 个，名字做成一个 `StrEnum`：`session.connect`、`case.ensure`、`case.save`、`case.close`、`basis.ensure_thermo`、`basis.ensure_reaction`、`basis.ensure_reaction_set`、`flowsheet.ensure_stream`、`flowsheet.ensure_reactor`、`flowsheet.set_spec`、`solver.solve`、`model.read_snapshot`。计划里的第 13 个 `session.restart` 属于后面的加固阶段。台账里确认过的调整优先于这份清单。

入参模型的约定：

- 每个工具的入参是一个 `BaseModel` 的子类。可区分的联合类型做成它的一个字段，不要把联合本身当作入参模型。
- 物理量一律带单位后缀，规范单位是 °C、bar（绝压）、kmol/h、kg/h、kW。换算到 HYSYS 使用的单位是 Backend 内部的事。
- 组成一律是摩尔分率，和为 1。物流的流量可以给摩尔流量或者质量流量，二选一。
- 反应的入参按反应类型做成可区分的联合类型：转化反应带基准组分和转化率，平衡反应带 Keq 来源。台账里记录的并行转化反应的排序设置，如果建模时需要，也是转化反应入参的一部分。
- 反应器类型、物性包、Keq 来源、热模式、可以被 `set_spec` 修改的变量，都用 `StrEnum`。反应器类型的枚举叫 `ReactorType`，包含五种（Conversion、Equilibrium、Gibbs、PFR、CSTR），在这里定义一次，全项目共用（代码体检的测试按这个名字检查哪些模块可以点名具体的类型）；本阶段的 Backend 只支持前三种，遇到后两种抛 `E_UNSUPPORTED`。其余枚举只列台账里验证过的取值。
- 反应器的进料是一个序列，可以有多股。`ensure_reactor` 的入参只有类型、连接、反应集、压降和热模式，不带出口温度。出口温度是工况变量，只通过 `set_spec` 设置。
- `set_spec` 可以修改的变量就是那个 `StrEnum`，它本身就是白名单。不在枚举里的值在入参校验时被拒绝。

结果的约定：

- 结果信封见计划 §9.3：成功时带状态（已创建、未改变、已更新）和这个工具自己的结果数据，失败时带错误码、消息、是否可重试和细节。结果数据是有类型的模型，不是裸 `dict`。§9.3 示例里的 `readback` 字段可以不要：读回比对在工具内部完成，不一致就是失败。
- 工具调用事件：工具名、入参、结果信封、耗时。下一阶段的 Trace 用它。
- `solver.solve` 成功时返回耗时和各对象的状态。失败时用错误码区分三种情况：等待超时是 `E_TIMEOUT`；模型缺少规定而没有解出来是 `E_NOT_SOLVED`，细节里带上各对象的状态文本；不收敛是 `E_NOT_CONVERGED`。
- `model.read_snapshot` 本阶段只做不带参数的全量读取。快照至少包含：
  - 物性包和组分表
  - 每个反应的类型、计量系数、类型参数；每个反应集的成员
  - 每股物流的温度、压力、摩尔流量、质量流量、各组分的摩尔分率，以及相态信息（气相分率，或者台账里记录的固体去向所需要的量）
  - 每股能流的热负荷
  - 反应器的类型、进出料和能流的连接、反应集、压降
  - 求解状态
- 快照里读不到的值是 `None`，不是 HYSYS 的空值哨兵数。哨兵数不应该离开 Backend。

#### 3. SimBackend 接口

`backends/base.py`：一个 `Protocol`，每个方法对应一个工具，入参和返回值都是 `spec/` 里的模型。它不提 HYSYS，也不提 COM。以后如果换仿真软件，只需要再写一个实现。

#### 4. 工具层

`tools/registry.py`：`ToolExecutor`，按名字调用工具。调用方传进来的是已经构造好的入参模型（非法的值在构造模型时就被 pydantic 拒绝了），所以这里不再校验一遍，只核对它是不是这个工具的入参类型。它依次做四件事：核对入参类型，调用 Backend，把 `ReactorAgentError` 转成失败的信封，记录耗时并把工具调用事件交给一个可选的回调（阶段 1C 的 Trace 会接在这里）。

执行器自己会遇到的两种错误：工具名不存在是 `E_TOOL_NOT_ALLOWED`；入参不是这个工具的入参类型是 `E_SCHEMA`。都不可重试。

`tools/definitions.py`：把工具名、入参模型、Backend 方法登记在一起。每个工具的入参类型不同，直接放进一张表容易写出 `Any`。一种通过了 `mypy --strict` 和项目 lint 规则的写法是用一个泛型函数把"核对入参类型"和"调用 Backend 方法"包成签名统一的可调用对象：

```python
ArgsT = TypeVar("ArgsT", bound=BaseModel)
ToolRunner = Callable[[BaseModel], ToolResult]


def bind(model: type[ArgsT], handler: Callable[[ArgsT], ToolResult]) -> ToolRunner:
    """把"核对入参的类型"和"调用处理函数"包成签名统一的可调用对象。"""

    def run(args: BaseModel) -> ToolResult:
        if not isinstance(args, model):
            return failure(ErrorCode.SCHEMA, f"入参应当是 {model.__name__}")
        return handler(args)

    return run
```

这里的 `failure` 代表构造失败信封的小函数，名字由你定。你可以用别的写法，只要没有 `Any` 和 `type: ignore`。工具层应当很薄。如果你发现在这里写业务逻辑，说明它应该在别处。

工具和 Backend 都不重试。计划 §9.3 表里的"重试"一列由下一阶段的执行器负责。

#### 5. 第一段的测试

单元测试，不需要 HYSYS。Backend 用测试文件里一个几十行的桩来代替，不要在 `src/` 里建假的 Backend。

- 入参模型拒绝非法值：负的流量、和不为 1 的组成、同时给了两种流量、白名单之外的变量。
- `ToolExecutor` 对未知工具、入参类型不对、Backend 抛错三种情况返回正确的信封；成功时回调收到一个事件。
- 可重试集合与计划 §13.2 一致。
- `tests/test_code_health.py` 通过。

### 第二段：HYSYS 实现

#### 6. HysysComBackend

`backends/hysys_com/`：实现 `SimBackend`。这是全项目最容易写乱的地方，注意以下几点。

- 这是把探针**收敛**成正式代码，不是复制探针。探针里一条直线写下来的调用，要按会话、Basis、流程图、读取四个关注点分到不同的文件里。动手之前先在进度文件里写出每个文件的职责和估计行数。
- 构造 Backend 对象时不连接 HYSYS，连接只发生在 `session.connect` 里。这样没有 HYSYS 的机器上也能创建对象、运行与它无关的测试。
- COM 异常的转换只写一处（一个上下文管理器或者装饰器），所有 COM 调用都经过它。不要在每个方法里各写一遍 `try/except`。
- 带单位的读和写各封装成一个小函数，其他代码不直接碰单位字符串。
- 三种反应器的差别（类型名、是否需要反应集、Gibbs 模式）用一张映射表或者几个小的私有函数表达，不要写成一个带着长 `if/elif` 的 `ensure_reactor`。
- 这里不做任何业务判断，不重试，不等待重连。出了问题就抛领域错误，怎么恢复由上层决定。
- 只使用台账里标为"已确认"的调用形式。标为"部分确认"的，只在备注写明的条件之内使用。
- 建模期间求解器是否要挂起、在哪一步挂起和放开，照探针里验证过的做法，并把它收在工具内部（比如新建空白 Case 时挂起，`solver.solve` 时放开并等待求解完成）。上层不应该需要知道这件事。`solver.solve` 的等待上限由入参给出，超过就抛 `E_TIMEOUT`。
- `session.connect` 的结果里放 HYSYS 的版本、进程号，以及这个实例是这次启动的还是复用了已经在运行的。后面的阶段靠后两项判断能不能结束这个进程：复用的实例可能是用户自己开着的，不能动。

`ensure_*` 的语义是"创建或确认"，规则只有三条：

1. 对象不存在：创建它，写入之后读回比对，返回"已创建"。
2. 对象存在，并且类型、连接、配置、规定值都与期望一致：什么都不做，返回"未改变"。
3. 对象存在但有任何一处不一致：抛 `E_CONFLICT`。

`ensure_*` 从不修改已有的对象。唯一会修改已有对象的工具是 `flowsheet.set_spec`，它只用于白名单里的工况变量（比如出口温度），设完读回。创建到一半失败留下的半成品，下一次 `ensure` 会报冲突，由上层丢弃整个 Case 重建；Backend 不负责清理。

#### 7. 集成测试

标 `hysys`，放在 `tests/integration/`。只通过 `ToolExecutor`，按台账里的调用序列建出三个模型。

- 结果与参照值的偏差在容差内：

  | 模型 | 对照 | 容差 |
  |---|---|---|
  | 转化反应器 | 出料五个组分的摩尔分率，对照计划 §17.2 的解析解 | 0.001 |
  | 平衡反应器 | 两个出口温度下出料五个组分的湿基摩尔分率，对照计划 §17.1 的参照值 | 0.02 |
  | Gibbs 反应器（含固体碳） | CO 收率，对照计划 §17.3 | 落在 38% 至 42% 之间 |

- 幂等：每个 `ensure` 工具紧接着再调一次，返回"未改变"，HYSYS 里的对象数量没有增加。
- 冲突：对一股已有的物流用不同的温度调用 `ensure_stream`，返回 `E_CONFLICT`。
- 快照里没有哨兵数：气相反应的液相出料流量为 0 或 `None`，不是一个巨大的负数。

测试的收尾要关闭 Case。用一个会话级的 fixture 管理连接，不要每个测试启动一次 HYSYS。

## 难点

**Backend 的大小。** 探针加起来有几百行，直接搬过来就是一个巨型文件。代码体检的测试会拦住超过 300 行的文件和超过 40 行的函数，所以先分好文件再动手。

**"一致"怎么判断。** `ensure` 要比较已有对象和期望值。浮点数用容差比较。组成、连接关系、反应的计量系数都要比。把"比较两个配置是否一致"写成独立的纯函数并做单元测试，它出错会导致幂等失效或者误报冲突。

**读回的时机。** 求解器被挂起时，有些量读回来是未知的。哪些量在写入后立刻能读回、哪些要等求解之后，以 0B、0C 的记录为准。

**不要把探针里"已存在就覆盖"的写法带进来。** 探针为了反复运行，常常直接覆盖已有的对象。正式的 `ensure` 遇到不一致必须报冲突。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- COM 异常只在一个地方捕获和转换：`com_error` 这个名字只出现在 `backends/hysys_com/` 的一个文件里。
- 单位字符串和空值哨兵只出现在读写封装的那个文件里，其他文件里搜不到。
- `ensure_reactor` 里没有按反应器类型展开的 `if/elif`，类型之间的差别在一张映射表里。
- "两个配置是否一致"的比较是独立的纯函数，有单元测试。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。
