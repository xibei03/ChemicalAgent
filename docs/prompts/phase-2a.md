# 阶段 2A：反应器选型

本文件是 `docs/prompts/phase-2a.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

到上一个会话（1C）为止，系统已经能把一份写好的规格文件变成 HYSYS 里经过验证的结果。从这个会话开始接入 LLM，分三步：这个会话做选型（判断用哪种反应器并说明理由），2B 做规格生成（把用户的描述写成规格），2C 做报告和端到端联调。

选型单独占一个会话，因为需求文档写明"选择正确的类型是评分的关键"。这一步错了，后面建得再好也不得分。

## 本阶段的目标

执行

```
reactor-agent run --text-file <一段反应过程描述.txt> --dry-run
```

系统输出反应器类型、判断理由、引用的原文依据、备选类型和不选它们的原因，不触碰 HYSYS。

并且有一套可以重复运行的选型评测，结果达到本文末尾的门槛。

## 选型的设计

这一段是本阶段的核心，先理解再动手。

一次 LLM 调用同时产出两样东西：从原文里抽取的**特征**，以及它**推荐的类型**和理由。然后代码用一套规则从特征独立推出一个结论，和 LLM 的推荐对照。这样做的原因是：LLM 擅长读懂原文，但它的判断不可审计；规则可审计，但读不了自然语言。两者结合，每个结论都能追溯到"原文哪句话 → 哪个特征 → 哪条规则"。

### 特征

下面是需要的特征和它们的确切含义。含义里的区分是选型对错的关键，写进 Skill 时要保留。取值为"是"的特征，以及"用户点名的反应器"不为空时，都要带一条原文依据。

| 特征 | 取值 | 含义 |
|---|---|---|
| 是反应过程的模拟请求 | 是、否 | 用户要模拟的是不是一个发生化学反应的过程。要模拟精馏塔、换热器这类，就是"否" |
| 用户点名的反应器 | 五种类型之一，或者空 | 用户明确说了用哪种反应器模型才算。"重整炉""气化炉""反应釜"是设备的叫法，不算点名 |
| 给出了动力学参数 | 是、否 | 原文里有速率常数、指前因子、活化能、反应级数这类数值 |
| 给出了设备尺寸 | 是、否 | 原文里有反应器的体积、管长、管径 |
| 设备形式 | 管式、釜式、未说明 | 用户说明了反应器是管式还是釜式 |
| 给出了转化率、收率或选择性的数值 | 是、否 | 作为**已知条件**给出。"请计算收率"是待求量，不算 |
| 反应已明确 | 是、否 | 用户写出了要模拟的全部反应式，或者点明了一个确定的反应，并且没有要求考虑没写出来的副反应。只写了"主要反应"、或者要求"考虑副反应"而没有把它们写出来，就是"否" |
| 黑箱类体系 | 是、否 | 气化、燃烧、裂解这类高温、非催化、机理复杂的过程（需求 §9.3），或者用户明说产物分布未知。反应式明确的催化可逆反应不属于这一类，温度高也不算 |
| 给出了平衡常数 | 是、否 | 原文里有 Keq 或 Ka 的数值或表达式。规则不用它，后面写规格时用 |
| 相态 | 气相、液相、多相、不明 | 反应物的相态 |
| 聚合反应 | 是、否 | 需求 §8 规定聚合反应不适用动力学反应器的规则 |

### 规则

规则分两层，由代码执行。

第一层判断每种类型能不能建，看的是必要的输入有没有：

| 类型 | 必要输入 |
|---|---|
| Conversion | 给出了转化率、收率或选择性的数值 |
| Equilibrium | 反应已明确 |
| Gibbs | 没有额外要求 |
| PFR、CSTR | 给出了动力学参数。设备尺寸缺失不影响选型，在结论里指出它是缺失的信息 |

用户没有给平衡常数不妨碍选 Equilibrium：需求 §8 说的是"提供 Ka 或 Gibbs 自由能"，没有 Ka 时由 HYSYS 按 Gibbs 自由能计算。

第二层在能建的类型里按下面的顺序取第一个。顺序来自需求 §8：

1. 用户点名的类型。点名的类型缺必要输入时，说明原因，继续往下判断。
2. 动力学反应器，聚合反应除外。在 PFR 和 CSTR 之间：先看设备形式，管式是 PFR，釜式是 CSTR；没有说明设备形式时看相态，气相是 PFR，液相是 CSTR；两者都定不了时，采用 LLM 的推荐。
3. Conversion。
4. 黑箱类体系选 Gibbs。
5. Equilibrium。
6. 以上都不满足，选 Gibbs。

第 4 条排在第 5 条前面，是因为燃烧、气化这类体系即使用户写出了一个主反应式，实际的产物分布也不是这一个反应能描述的（需求 §8 对 Gibbs 的说明，§9.3）。

聚合反应遇到第 2 条时跳过它，按后面的顺序判断，并在结论里注明这是需求 §8 规定的例外。

### 对照

规则结论和 LLM 的推荐一致就通过。不一致时带着分歧重问一次，要求 LLM 对照原文重新核对特征，因为分歧通常来自某个特征抽错了。仍不一致时采用规则结论。

最终的选型结果（`SelectionResult`）包含：

- 反应器类型，以及它是怎么定的（两者一致，或者采用了规则结论）。
- 规则这一侧的说明，由代码生成：哪些类型能建，命中了第二层的哪一条，依据哪些特征。这样即使 LLM 的推荐被推翻，输出的理由也和结论对得上。
- LLM 的推荐和它的理由。被推翻时，它作为备选列出。
- 全部特征和它们的原文依据。
- 备选：其余能建的类型各列一条，写明不选的原因。LLM 给了原因就用它的，没给的由代码写"优先级低于所选类型"。不能建的类型由代码写明缺什么。

需求 §8 末尾说"没有固定的反应器类型，只有合不合适"。所以输出里永远带备选和不选的理由。

两种不往下走的情况，终态都是 `UNSUPPORTED`，选型结论和理由照常输出：

- "是反应过程的模拟请求"为否。
- 选出的类型在 Recipe 注册表里查不到（现在是 PFR 和 CSTR）。判断依据是注册表，不要把类型名写死在执行器里。

## 任务

### 1. 先写评测用例

在写 Skill 之前先把评测用例写完并提交，这样用例不会被你对 Skill 的了解带偏。

`evals/cases/`：按计划 §15.3 的表，每个用例一个 YAML，包含输入文本、期望的类型、期望的关键特征。本阶段用到表里除了 L1-X1 至 L1-X4 之外的用例，那四个是 2B 的。

三个考核场景的输入从 `docs/REQUIREMENT.md` 逐字复制，包括错别字和全角符号，只去掉行首的 `>` 和 `**`：

| 场景 | 取哪几行 |
|---|---|
| 场景 1 | 第 42 至 46 行 |
| 场景 2 | 第 51 至 52 行 |
| 场景 3 | 第 57 行和第 60 行 |

第 36、37、62 行是出题人对考生说的话，不属于任何场景的输入。

其余用例由你编写，覆盖表里列的每一类。它们用的体系不能与留出场景重合（计划 §15.7：乙醇脱水、合成氨、甲烷与空气燃烧），那些要留到阶段 3A 检验泛化。

### 2. LLM 客户端

`llm/client.py` 定义接口：给它系统提示、用户内容和一个 pydantic 模型类型，返回这个类型的实例，连同这次调用的记录（模型名、耗时、token 数、提示和回复的全文）。`llm/providers/` 下按 `docs/progress.md` 记录的供应商实现一个。把这家供应商的官方 SDK 加进 `pyproject.toml` 的依赖；它是计划内的依赖，不需要问我。

- 温度设为 0。模型不允许时用它允许的最低值。
- 用供应商原生的结构化输出能力，拿到结果后再用 pydantic 校验一遍。校验不过时带着错误信息重问一次，再不过就抛 `E_LLM`。
- 超时设成明确的数值（60 秒左右），网络错误的重试用 SDK 自带的配置并限制次数，不自己写循环。演示时网络不通，不能让系统卡上几分钟。
- 客户端不写文件，也不写 Trace。调用记录由执行器保存：摘要进 Trace，全文进运行目录的 `llm/` 子目录。密钥不落盘。
- 每次调用是无状态的，不带之前的对话。

`config/settings.yaml`：供应商、模型名、密钥所在的环境变量名、超时。密钥本身不进文件。由 `cli.py` 读取并传给客户端。

`llm/prompts/system.md`：很短的系统提示，三个调用点（选型、写规格、写解读）共用，所以只写对三者都成立的规则：不做算术和单位换算；原文没有的信息不能悄悄补上，只能声明缺失，或者作为带理由的假设；只按给定的结构输出。

### 3. Skill 加载

`skill_loader.py`：按名字加载一个 Skill，解析 `SKILL.md` 开头的元数据（名称、说明、版本、用在哪个状态）和正文，按需加载 `references/` 下的文件，读出 `rules.yaml`，并算出内容哈希供 Trace 记录。`skills/` 目录的位置由调用方传入。

### 4. 选型 Skill

`skills/reactor-selection/`，结构见计划 §8.4。

- `SKILL.md`：任务、特征的定义、输出要求（每个判断引用原文依据，依据必须是原文里的原话）。
- `references/selection_rules.md`：需求 §8 和 §9 里的选型知识，用你自己的话整理，保持原意。
- `references/pitfalls.md`：容易判错的情况，写成一般性的原则，例如"被要求计算的指标不是已知条件""提到炉、管、釜不等于给出了动力学""给出了主反应但要求考虑未列出的副反应，等于反应没有明确"。
- `rules.yaml`：两张表。每种类型的必要输入（哪些特征必须为"是"），以及第二层的优先顺序。在 PFR 和 CSTR 之间怎么选、聚合反应的例外，写在代码里。
- `examples/`：两三个示例。

Skill 里能写什么、不能写什么，界线在这里：

- 能写：判断标准，以及一般性的工艺知识。需求 §8、§9 的内容属于这一类，例如"气化、燃烧、裂解这类高温、机理复杂的体系，产物分布由热力学平衡决定"。
- 不能写：三个考核场景的原文或改写、场景里的具体数值、"某某工艺用某某反应器"这样的对照表。
- 检验方法：把三个场景换成同类的其他体系，Skill 一个字都不用改，仍然适用。

这样要求有两个原因：把场景写进 Skill 等于把答案硬编码进系统，而需求要求的是自主判断；评测集用的就是场景原文，Skill 和评测重合会让准确率虚高。

示例用的体系不能与评测用例和留出场景重合。可以用环氧乙烷水合、乙苯脱氢、二氧化硫氧化这类。

### 5. 选型结果和规则检查

`spec/selection.py`：`SelectionResult` 及其组成部分的模型、规则表的模型，以及规则检查。规则检查是纯函数：输入是特征和规则表，输出是能建的类型、规则结论和规则这一侧的说明。它自己不读文件；`rules.yaml` 由 `skill_loader` 读成规则表的模型再传进来。

原文依据的检查也放在这里，同样是纯函数：每条依据必须是输入文本的子串。比较之前对两边做 Unicode 规范化（NFKC）并去掉空白，否则 `C₇H₈` 和 `C7H8`、`℃` 和 `°C` 这类差别会造成误判。

### 6. SELECT 状态

给任务加第二种入口：输入是一段文字时，任务从 SELECT 开始；输入是规格文件时照旧从 PLAN 开始。

在执行器的状态表里加 SELECT。处理函数只做编排，每一步调用别处的函数：组装上下文（系统提示、Skill、用户原文）→ 调 LLM → 检查原文依据 → 规则检查 → 有分歧或者有依据不是原文时重问一次 → 得出最终结果 → 完整的结果保存到运行目录的 `artifacts/selection.json`，`TaskState` 里只存类型和它是怎么定的。上下文的组装放在 `harness/context.py`。

重问只有一次机会，分歧和无效依据合在一起问。重问之后仍然不是原文的依据，丢掉它并在 Trace 里记录。重问的次数上限写进 `harness/budgets.py`，和其他回路上限放在一起。

给 Trace 加 LLM 调用事件（调用点、模型名、Skill 名和内容哈希、token 数、耗时），时间线里要显示出来。

### 7. 命令行

- `reactor-agent run --text-file <文件>`：从 UTF-8 文件读入描述。再支持把文本直接作为位置参数传入（`reactor-agent run "<文本>"`），但文档和示例里用文件：一长段带引号的中文作为命令行参数，很容易被 shell 改坏。
- `--dry-run` 在 SELECT 之后停下并打印选型结果，用的是 1C 做的"推进到指定状态后停下"。正常停下时退出码是 0。它不需要 HYSYS，所以不要创建或连接 Backend。
- 现在 SELECT 之后还没有下一个状态（规格生成在 2B）。不带 `--dry-run` 的文本输入也在这里停下，并说明后续步骤尚未实现。

### 8. 评测

`evals/run_evals.py`：对每个用例运行选型，三个原文场景各重复 5 次，其余各 1 次。输出类型准确率、重复运行的一致性、关键特征的准确率，写入 `docs/EVAL_RESULTS.md`，同时记录模型名、Skill 版本和提交哈希。同时记录 LLM 原始推荐的准确率和最终结论的准确率，两者的差别说明规则起了多大作用。

### 9. 测试

- 规则检查：第二层的每一条至少一个用例，包括"点名的类型缺必要输入""聚合反应""黑箱类体系写出了反应式"。
- 原文依据检查：全角半角、上下标、空白不同但内容相同的依据算通过；原文里没有的算不通过。
- SELECT 处理函数：用一个返回预设结果的 LLM 桩，覆盖一致、重问后一致、始终不一致、不是反应过程、选出的类型没有 Recipe 五条路径。
- LLM 客户端：用桩替换网络层，覆盖输出非法后重问成功、重问仍非法两种情况。
- Skill 加载：元数据解析和哈希。
- Skill 内容：把三个场景的输入和 `skills/` 下每个文件的内容都做 Unicode 规范化（NFKC）并去掉空白，然后取场景输入里所有长度为 12 的连续片段，断言任何 Skill 文件都不包含其中任何一个。这个测试对后面阶段新增的 Skill 同样生效。它查得出照抄，查不出改写和单个数值，后两者靠你自己把关。
- 真正调用 LLM 的测试标 `llm`，只保留一个冒烟测试。模型的实际表现由评测来衡量。

## 难点

**评测没达标时怎么改。** 只允许改一般性的规则和特征定义，不允许往 Skill 里加针对某个用例的措辞。每次修改都在进度文件里记一句：哪个用例错了，原因是什么，改了哪条一般性的规则。如果你发现自己在写"当原文提到某某时"这样的句子，停下来重新想。

**特征和结论一起错。** 如果 LLM 把"要求计算收率"抽成了"给出了收率"，规则和推荐会一致地得出错误结论，对照发现不了。防线是特征定义写得足够清楚，以及评测里的对抗用例。

**处理函数变成大杂烩。** SELECT 有六七步，全写在一个函数里就超过了行数上限，也没法单独测试。规则检查和依据检查在 `spec/selection.py`，上下文在 `harness/context.py`，处理函数只把它们串起来。

**供应商之间的差别。** 结构化输出的做法各家不同，把差别封在 `llm/providers/` 里，接口保持最小。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- SELECT 的处理函数只做编排，里面没有规则判断和字符串处理。
- 规则检查和依据检查是 `spec/selection.py` 里的纯函数，不读文件，不调 LLM。
- 各家供应商的差别只在 `llm/providers/` 里，`llm/client.py` 的接口里看不出是哪一家。
- 三处"带着问题重问 LLM"（客户端的校验重问、选型的分歧重问、后面 2B 的规格重写）各在各的层，没有写成三份相似的循环。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。

## 本阶段不做

- 不做规格生成、规范化和业务规则校验，那是阶段 2B。
- 不做报告。
- 不触碰 HYSYS，不修改 `backends/`、`tools/`、`recipes/`、`validation/`。

## 完成标准

1. `ruff format --check .`、`ruff check .`、`mypy src`、`pytest` 全部通过。
2. 三个场景的输入各自执行 `--dry-run`，分别输出 Equilibrium、Conversion、Gibbs，带理由、原文依据和备选。
