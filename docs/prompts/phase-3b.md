## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

三个考核场景和一批留出场景已经跑通。需求文档 §8 的选择逻辑里，第一条规则就是动力学反应器：用户给出动力学参数和设备参数时，气相用 PFR，液相用 CSTR。系统现在能正确判断出这两种类型，但还不会在 HYSYS 里建它们，遇到时返回"暂不支持"。如果考核给的额外场景恰好是这一类，系统只能答对一半。

这个会话是可选的，只在前面的阶段都完成并且还有时间时才做。三项任务按价值排序，做到哪一项算哪一项。每做完一项都要确认三个考核场景没有退步。

## 任务 1：PFR 和 CSTR

这项任务要用到台账里还没有的 HYSYS 接口，所以**先探索，再实现**，和阶段 0 的做法一样。

### 探索

在 `spikes/` 下写探针，弄清并记入台账：

- 动力学反应怎么用代码创建：速率表达式的形式、指前因子、活化能、各组分的反应级数、速率的基准（浓度还是分压）、反应发生的相。
- PFR 和 CSTR 的类型名，各自必须规定哪些量才能求解（PFR 的管长、管径、管数；CSTR 的体积），热模式怎么设。
- 反应集怎么挂到这两种反应器上。

需要参考 Case 时，先在 HYSYS 自带的示例里找；找不到再请我手工建一个。台账没有确认之前，不要在 `src/` 里写对应的代码。

### 实现

- `ModelSpec` 增加动力学反应和两种反应器的参数段。
- `recipes/pfr.py`、`recipes/cstr.py`，登记进注册表。
- Backend 增加对应的分支，只用台账里已确认的调用。
- `skills/reactor-modeling/references/` 增加 `pfr.md` 和 `cstr.md`。
- 按照计划 §23.1，这些改动不应该涉及 `harness/`。

### 验证

用有解析解的用例验证，因为动力学参数最容易错在单位上，而单位错了模型照样能求解，只是结果不对。

- PFR：等温、一级不可逆、反应前后摩尔数不变的气相反应（A → B）。体积流量恒定时，转化率 X = 1 − exp(−k·τ)，τ 是反应器体积除以入口条件下的体积流量。
- CSTR：等温、一级不可逆的液相反应，X = k·τ / (1 + k·τ)。
- 一级反应的速率常数只有时间的量纲，浓度单位的错误在一级用例里全部抵消，查不出来。所以每种反应器再加一个二级反应的用例（2A → 产物，速率 = k·C²，摩尔数不变或液相）。令 a = k·C₀·τ，C₀ 是入口处 A 的摩尔浓度，由测试从 HYSYS 读回的入口条件算出：PFR 是 X = a / (1 + a)；CSTR 是 X = [(2a + 1) − √(4a + 1)] / (2a)。
- 再加一个用指前因子和活化能（而不是直接给 k）的用例，核对活化能的单位。

这些解析解只在等温、压降为零、体积流量恒定时成立。测试里先断言这几个前提（出口温度与进口相差不超过 1 K，压降为 0），再比较转化率；气相用例取低压，避免非理想性改变体积流量。HYSYS 用来积分的有效体积（比如 CSTR 的液位、PFR 的空隙率）以台账的记录为准，解析解用同一个体积。

选一组让转化率落在 30% 到 80% 之间的参数，HYSYS 的结果与解析解相差不超过 2 个百分点算通过。

先做 PFR，再做 CSTR。只做完 PFR 也算这项任务部分完成，在进度文件里写明。

留出用例 HO-4 是气相 PFR，现在应当能端到端完成。把它的期望终态从"不支持"改成"完成"，单独提交并在提交信息里写明原因。HO-4 的参数如果超出了这次实现的范围（单个反应、幂函数速率式、按浓度计），系统应当把超出的地方作为问题返回。

## 任务 2：组分解析增强

现在遇到 `config/components.yaml` 里没有的组分，系统会报错并给出别名表里名字相近的候选。这对额外场景不够，因为别名表只覆盖了常见组分。

规格的校验在 `spec/` 里，它不能调用 HYSYS。所以做法是预先导出：写一个探针脚本，把 HYSYS 组分库整体导出成一个数据文件（`config/components_library.yaml`：规范名、分子式、分子量）。规范化在别名表没有命中时，到这个文件里按名称和分子式查找。唯一匹配就采用，并把这次解析登记为一条假设（"某某按 HYSYS 组分库中的某某处理"）；有多个候选就把候选交给规格重写那一轮，由 LLM 在候选里选，不允许选候选之外的名字。

如果台账的结论是组分库无法整体导出，这一项就不做：阶段 3A 已经把别名表扩充到了常见组分。

## 任务 3：转化反应器的平衡可行性校验

需求 §9 在讲甲苯歧化时特别提到："不是想转化多少就转化多少，受化学平衡参数的影响较大"。一个懂工程的系统应该能指出用户设定的转化率是否超过了平衡极限。

做法是复用已有的能力，并且不改动执行器：

- 主任务完成之后，由 `cli.py` 用一个 `spec/` 里的纯函数从主任务的规格派生出第二份规格：同样的组分和进料，Gibbs 反应器，温度取转化反应器求解出的出口温度，压力取出口压力。
- 用同一个执行器把它作为第二个任务跑一遍（新的 Case），记下它来自哪个任务。
- 把得到的平衡转化率写进主任务运行目录的 `artifacts/equilibrium_check.json`，然后重新渲染主任务的报告。报告看到这个文件就多出一节，把平衡转化率和用户设定的转化率并列。

这一节是报告里的提示，不是一项检查，不改变主任务的终态。设定值比平衡值高出 1 个百分点以上时写明"设定的转化率超过了平衡极限"，相差在 1 个百分点以内时写"接近平衡极限"。附加计算失败时，主任务的结果和终态不受影响，报告里注明"未能计算平衡转化率"。

## 难点

**速率常数的单位。** 指前因子的单位取决于反应级数和速率基准，HYSYS 对它的单位有自己的要求。代码不应当默默换算。用户给的单位能对应到 HYSYS 支持的形式就用，对应不上就作为问题返回并说明原因。

**探索的时间盒。** 动力学反应的创建接口和阶段 0 的转化反应一样没有公开文档。针对同一步换了 5 种思路仍不通，就记录现状，把这项任务标为未完成，转去做任务 2。不要让它拖垮整个会话。

**回归。** 每完成一项任务，重新跑三个考核场景的评测和端到端测试。
