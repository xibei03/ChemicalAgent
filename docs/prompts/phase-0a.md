# 阶段 0A：环境自检、连接 HYSYS、反向探测

本文件是 `docs/prompts/phase-0a.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要在 3 天内做出一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。全局设计在 `docs/MASTER_PLAN.md`。

整个项目只有一件事没有把握：Python 能不能通过 COM 在 HYSYS V15 里**创建**反应、反应集和反应器。目前查到的官方公开资料只说明了如何连接和读写已有的对象。所以前三个会话（0A、0B、0C）全部用于探索。这个会话是第一步：把环境立起来，连上 HYSYS，弄清它的 COM 对象模型里有什么。

探索过程本身是考核的评分项。试过什么、结果如何、为什么放弃，都要留下记录。走不通的路线同样要记，它们会直接写进考核报告。

## 本阶段的目标

会话结束时，下面四件事成立：

1. 仓库已经初始化，质量工具（ruff、mypy、pytest）可以运行。
2. 有脚本证明 Python 能连接 HYSYS V15，能打开一个已有的 Case，读出物流的温度、压力、流量、组成，改写温度、压力、流量，并控制求解器。
3. 知道 Conversion、Equilibrium、Gibbs 三种反应器，以及反应、反应集，在 COM 里的类型名和成员清单。
4. 以上结论连同证据写进了 `docs/HYSYS_INTEGRATION.md`。

## 难点

**早绑定和晚绑定。** 用 `Dispatch` 得到的晚绑定对象，`dir()` 几乎看不到成员。用 `EnsureDispatch` 的早绑定能看到成员，但属性名区分大小写，而且从集合里取出的对象可能只暴露基类接口，要访问反应器特有的成员可能需要 `win32com.client.CastTo`。遇到"成员不存在"时，先确认是接口不对还是名字不对。把最后哪种绑定方式可行记进台账，后面所有代码都要沿用。

**阻塞。** HYSYS 弹出模态对话框（许可证提示、保存确认）时，COM 调用会一直不返回。调用卡住超过一分钟，请我看一眼 HYSYS 窗口。

**残留进程。** 反复运行脚本容易留下多个 HYSYS 进程。开始新探针之前检查一下。

**命令行的差别。** 你用的 shell 可能会改写命令的参数。比如在 Git Bash 里，`reg query` 的 `/f` 这类开关会被当成路径。遇到这种情况换用 PowerShell 或 cmd，或者改用 Python 的 `winreg` 模块。

**不要凭记忆写调用。** 计划、公开教程和你的训练数据里的 HYSYS 调用，大多来自十几年前的版本。每一个调用形式都以这台机器上的实际运行结果为准。

**时间不要花在全量枚举上。** 类型库有上千个成员，把它们全部列出来不是目的。目的是回答三个问题：三种反应器叫什么、它们的设置在哪些成员上、哪些接口可能用来创建反应。
