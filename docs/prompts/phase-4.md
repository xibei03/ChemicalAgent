# 阶段 4（可选）：加固——故障测试、自动恢复、中断续跑

本文件是 `docs/prompts/phase-4.md`。如果对话被压缩过，或者你不确定现在该做什么，重新读这个文件、`CLAUDE.md` 和 `docs/progress.md`。

## 你在做什么

这个项目要做一个系统：读入一段中文的反应过程描述，判断该用哪种反应器，在本机的 Aspen HYSYS V15 里真实地建模、求解并返回结果。

系统已经能跑通三个考核场景和一批留出场景。目前的恢复能力是最小的一套：步骤重试、干净重建、带诊断中止。它们只在真实运行中被偶然触发过，没有被系统地测试过。这个会话把执行器的可靠性从"看起来能用"提高到"有测试证明"。

这个会话是可选的，排在泛化之后，因为需求文档的评分项里没有续跑和故障注入。只在前面的阶段都完成并且还有时间时才做。五项任务按价值排序，做到哪一项算哪一项。

有一条贯穿这个会话的约束：**加固不能让主路径变复杂。** 三个场景正常运行时走过的代码，应当和现在一样直白。如果某项加固需要在主路径上到处加判断，那它的设计有问题。`harness/` 的规模上限仍然是 600 行代码，由 `tests/test_code_health.py` 检查。

## 本阶段的目标

1. 有一个不需要 HYSYS 的假 Backend，和一组用它跑的执行器测试，覆盖幂等、每类故障的恢复路径、预算耗尽、完成判定。
2. HYSYS 进程失效时，系统能自动重启会话并重建。
3. 任务中断后，可以从中间继续。
4. 解读文字里的数字、选型的关键特征，各有一道与 LLM 无关的检查。

## 任务 1：假 Backend 和执行器测试

`backends/fake.py`：实现 `SimBackend` 接口，把模型保存在内存里。它不做任何化工计算；求解时按一个可配置的简单规则给出料填上数值，够让验证检查通过或者失败即可。它要支持注入故障：指定在第几次调用哪个方法时抛出哪个错误码。

`tests/harness/`：用假 Backend 实现计划 §15.4 的测试矩阵。

| 测试 | 断言 |
|---|---|
| 幂等 | 同一份计划连续执行两遍，第二遍没有创建任何对象 |
| 故障注入 | 对 Backend 能抛出的每个错误码，在每一类步骤（PREFLIGHT、BUILD_BASIS、BUILD_FLOWSHEET、SOLVE、VERIFY）上注入一次，恢复路径和终态与计划 §13.2 的策略表一致。预期值照 §13.2 另写一张表，不要从 `recovery.py` 里导入，否则表错了测试也跟着错 |
| 预算 | 注入永久性的失败，系统在上限之内到达 FAILED，不会一直重试 |
| 完成判定 | 注入致命的检查失败，终态不可能是 COMPLETE |

故障注入的用例用参数化测试生成，不要手写几十个几乎一样的测试函数。断言的对象是：Trace 里恢复事件的序列、终态、工具调用总数的上界。

1A 和 1C 的测试里各有一个小的桩。有了假 Backend 之后，能用它替换的就替换掉，不要留三份功能重叠的桩。

这些测试暴露出执行器的缺陷时，先写下缺陷，再修。修的时候保持 `engine.py` 和 `recovery.py` 的结构清楚：恢复策略仍然是"错误码 → 策略链"的一张表，不是散落各处的条件判断。

## 任务 2：自动重启会话

现在 HYSYS 进程失效时，系统直接中止，由人重启后重跑。

- 增加工具 `session.restart`：按记录的进程号结束旧进程（`taskkill /F /PID`，不引入第三方库），确认进程已经退出之后再启动新会话。只结束自己启动的那个进程：`session.connect` 的结果里有"是否复用了已有实例"，复用的实例可能是用户自己开着的，这时不重启，按原来的做法带诊断中止。
- 在恢复策略里加入这一级，涉及 `E_COM_UNAVAILABLE`、`E_COM_DISCONNECTED`、`E_TIMEOUT` 三个错误码（见计划 §13.2）。重启之后 Case 已经没有了，所以"重启"和"干净重建"是合在一起的一步，占用任务仅有的那 1 次重建。
- 在假 Backend 上测试这条路径。再在真实的 HYSYS 上验证一次：任务运行到一半时结束 HYSYS 进程，系统应当自己恢复并完成。建模只要几秒，手工掐不准；阶段 1C 的会话失效试验用过一个"第 N 次工具调用之后结束进程"的脚本（看进度文件），复用它。验证前提醒我保存 HYSYS 里别的工作。

## 任务 3：中断续跑

命令 `reactor-agent resume <task_id>`，流程见计划 §13.3。

- 给 `TaskState` 和 Trace 加上运行序号（1C 当时没有加），续跑一次加 1，这样时间线里分得清两次运行。
- 在 Basis 建完、流程图建完两个时点各保存一份 `.hsc` 快照。每个工况求解后的 `.hsc` 1C 已经在存，它也是可用的检查点。
- 续跑时：读状态文件。任务还没到建模阶段，就从那个状态继续，已经冻结的 LLM 产物不重新生成。已经进入建模阶段，就打开最近的有效快照，把 HYSYS 里的现状和计划对一遍，从第一个没有满足的步骤继续。
- 快照有效的条件：规格的哈希没变，文件存在，打开后与计划不矛盾。不满足就退回更早的检查点，最差情况是从空白 Case 重建。
- 测试：在假 Backend 上，在每个状态之后中断，续跑后的终态与不中断时一致，LLM 的调用次数不增加。

因为工具是"创建或确认"的语义，续跑的核心其实只是"重新执行计划，已经存在并且一致的步骤自然跳过"。如果你的实现比这复杂很多，重新想一想。

## 任务 4：与 LLM 无关的两道检查

- **数字回查。** 解读文字里的数字必须能在报告的表格里找到。只检查带小数点、百分号或单位的数；反应式里的系数、分子式和编号里的数字不算。按解读里写出的有效位数比较。找不到时，丢弃解读文字，生成不含解读的报告，并在 Trace 里记录。测试里要有一个不该被误判的用例和一个该被查出的用例。
- **特征的原文证据。** 对选型最关键的三个特征（给出了转化率或收率的数值、给出了动力学参数、给出了平衡常数），用简单的文本规则在原文里找证据。LLM 说"给出了"而原文里找不到任何对应的数值表述，就把这个矛盾并入 2A 已有的那一次重问，不另外增加重问的次数。规则是旁证，不直接推翻 LLM 的结论。规则写成 `spec/selection.py` 里的纯函数。

## 任务 5：全局预算和工具权限

- 状态迁移总数和任务总时长的上限，见计划 §7.4。超过时终态是 `FAILED`，错误码 `E_BUDGET`。时钟要能在测试里替换，否则测试得真的等上 15 分钟。
- 状态到工具组的白名单，见计划 §7.3 的表。主路径上只有执行器调用工具，所以这是一道防程序缺陷的保险，实现应当很小：在执行器调用工具的那一个入口检查，违反时是 `E_TOOL_NOT_ALLOWED`。

## 难点

**假 Backend 容易做成第二个 HYSYS。** 它只需要记住有哪些对象、各自的配置是什么，以及在被要求时出错。不要在里面写任何反应计算。控制在约 200 行。

**测试执行器，不是测试假 Backend。** 断言的对象是状态迁移、恢复路径、终态和工具调用序列。

**续跑的边界情况很多。** 先让最常见的情况（建模中途中断）工作并有测试，再考虑其他情况。做不完的情况退回"从空白 Case 重建"，这永远是正确的。

## 代码质量

这个阶段写的代码，后面的会话会接着往里加东西。它们只读得到代码，读不到你现在的思路。所以代码规范（`CLAUDE.md`）和功能一起验收：时间不够时可以少做功能并如实说明，不可以放松规范。

本阶段最容易写乱的地方，以及怎样算做到了：

- 三个场景正常运行时走过的代码，和加固之前一样直白；加固的逻辑在旁路上。
- 恢复策略仍然是"错误码 → 策略"的一张表。
- 假 Backend 里没有任何化工计算。

写每个模块之前，先想清楚它唯一的职责和对外的接口。收尾时按 `CLAUDE.md` "收尾前的代码体检"做那三件事，结果写进交接报告。

## 本阶段不做

- 不做由 LLM 提出修复补丁的回路。它是全部加固项里最复杂、最可能引入不稳定的一项，除非我明确要求。
- 不做新的反应器类型和新的建模能力。
- 不为加固而重写执行器。
- 不做任务锁。

## 完成标准

1. `ruff format --check .`、`ruff check .`、`mypy src`、`pytest` 全部通过。
2. 做了任务 1 的话：测试矩阵全部通过，并且不需要 HYSYS。
3. 做了任务 2 的话：在真实 HYSYS 上手动中断一次，系统自己恢复并完成。
4. 做了任务 3 的话：续跑测试通过；在真实 HYSYS 上中断并续跑一次成功。
5. 做了任务 4 的话：两道检查各有通过和不通过的单元测试。做了任务 5 的话：超出上限和越权调用各有一个测试。
6. 三个考核场景和留出场景的评测、端到端测试没有退步。
7. `tests/test_code_health.py` 通过，其中的上限没有被改动。主路径的代码没有因为加固而变得更难读。交接报告里有 `python tests/test_code_health.py` 的输出，以及按 `CLAUDE.md` 做代码体检的发现和处理结果。
8. `docs/progress.md` 已更新，改动已分多次提交。

时间盒：任务 1 约 1.5 小时，其余每项约 1 小时。

时间不够时的取舍：五项任务按顺序做，做完一项、回归通过、提交，再做下一项。做到一半的任务如果让回归退步，回退它。
